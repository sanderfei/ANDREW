# OBS-33：OBS本地下载大制品中途收到HTTP2对端重置

项目：g_web_installer。记录日期：2026-11-10。状态：截图及当前源码分析；对端原因和完整下载待验证。

环境：用户提供 Web 的 OBS V3 本地下载任务截图，目标是 KK 离线制品；用户后续展示了 nerdctl 下运行中的 Web 容器。现场运行版本、网络路径及主机状态未由本轮独立核实。源码分析基于本地 release 9c6bf3ca408b，不能推断现场运行相同版本。

## 现象与边界

任务 11:02 开始，总量 7748.16 MiB；11:23 进度为 1188.84 MiB，11:26 为 1193.80 MiB，随后 11:26:21 报错：

```text
save local download: stream error: stream ID 11; INTERNAL_ERROR; received from peer
```

任务下载正文过程中失败；11:26 的数字是采样进度，不必然是最终接收字节数。结束日志 Completed 只表示操作结束，不代表下载成功。后三分钟增量约 4.96 MiB，说明该时间段相较之前变慢，不能据此断定限速或具体故障原因。

HTTP/2 的 stream error 由连接对端发来的流重置表示；INTERNAL_ERROR 是对端报告的通用内部错误，见 [RFC 9113 第 5.4.2 和 7 节](https://www.rfc-editor.org/rfc/rfc9113.html#section-5.4.2)。对端可能为 Web 实际连接的网关或前置代理，错误不包含内部根因，不能确定哪一层失败，也不能由此认定磁盘不足、凭据失效或 Web 本地超时。相似症状的历史版本导入见 [OBS-29](OBS-29.md)，本次为不同任务，不能直接套用其原因或现场状态。

## 当前源码行为

`g_web_installer/internal/service/file_server/obs_v3_local_download.go:39-59` 发起异步本地下载，取得 HTTP 200 响应后保存；`:109-136` 中将响应体经 `io.Copy` 写入同目录临时文件，出错时返回 `save local download` 并尝试删除临时文件；完整写入、长度检查和关闭成功后才 rename 为正式文件。失败时已有正式文件保留，不能把已存在的旧文件当成本次下载成功。该实现无下载中断后的续传和业务重试；重新提交会从头下载。异常进程退出、文件删除失败或现场旧版实现的行为均未核实。

`internal/service/file_server/obs_v3_progress.go:11` 当前源码每三分钟记录一次进度，是采样周期，并非三分钟超时。现场二进制及有效超时未知。

## 后续出现本地路径占用提示

用户接续反馈 `this local path is being downloaded or imported`。当前源码在提交本地下载前以目标路径为键使用进程内 `sync.Map` 占用；本地镜像导入也使用同一锁。重复请求立即拒绝，不会创建新下载任务。锁先于目录操作锁获取，因此新任务即使仍在等待目录操作锁、尚未开始传输，也可能占用该路径。

按当前源码，截图中这次下载函数返回时先释放路径锁，之后 executor 才记录 `Completed`。若确认同一实例、同一任务及同版本，旧任务的 Completed 已写出仍出现占用提示，需要检查是否随后有新下载或本地导入正在使用相同目标路径、是否有任务等待，以及实际请求被路由到哪个实例；不能仅凭该提示认定死锁或旧失败任务仍持锁。各实例锁相互独立；现场版本、实例和活跃任务尚未确认。参见 `internal/service/file_server/obs_v3_local_download.go:35-42`、`obs_v3_local_import.go:91-115` 与 `obs_executor.go:95-117`。

## 单任务取消能力边界

用户询问如何手动关闭单个下载 PID。当前源码中的 PID 是 `ObsExecutor` 生成的任务标识，下载在 Web 进程内以 goroutine 执行，并非独立系统进程。OBS V3 路由提供任务日志查询，未提供按 PID 取消本地下载的接口。现有 `/api/v1/execute/:owner_type/:owner_name/kill/:pid` 操作的是 `command` 包独立的运行任务注册表；OBS 下载没有注册到该表，不能用于停止该任务。参见 `internal/service/file_server/obs_executor.go:43-63`、`internal/service/command/execute_kill.go:21-31` 和 `internal/service/command/execute.go:20-43`。现场版本未核实。

正常等待下载成功、失败或超时退出后会释放路径锁；等待目录操作锁时，超时后也要等拿到该锁才会检查上下文退出。结束 Web 进程会影响该实例的全部任务，异常退出可能留下临时文件；本轮未执行重启或停止。删除临时文件或日志不能取消任务或释放进程内路径锁。实现按 PID 精确取消需要单独开发和验证，并处理等待锁时响应取消；此处是方案建议，尚未实现。

## 14:03 新任务尚未显示传输进度

用户重新触发本地下载，提供的 14:03 任务日志只有 Started、Owner 和 UserId，未见 OBS real_path、Local path、下载进度或终态；用户提供的容器日志持续出现 `[Writer] Ping sent successfully`。当前源码在记录 UserId 之后尝试获取全局目录操作锁，获取成功后才打印 OBS real_path 和 Local path，再发出下载请求。因此该任务可能正在等待目录操作锁，但现场版本、日志完整性、锁持有者和任务实际状态均未核实，不能据此断定死锁或文件正在传输。参见 `internal/service/file_server/file_server_v3.go:83-92`、`obs_v3_local_download.go:39-51`。

当前源码的 `[Writer] Ping` 是日志 WebSocket 的心跳，不是文件下载进度，参见 `internal/service/log/tail.go:57-89`。应结合该 PID 完整任务日志、其他目录操作的任务日志及运行实例进行只读排查，观察后续是否出现路径、周期进度或终态；确认持锁来源前不删除数据、不重启。该次下载是否完成和故障是否恢复仍待验证。
