# BK-35：Neo4j历史包补开APOC导出配置且重启后保留

项目：g_web_installer、g_kube_installer。记录日期：2026-10-21；更新日期：2026-10-29。记录状态：本轮客户已成功交互进入 Pod、登录数据库并确认 APOC 导出过程注册；当前客户实际文件导出、Web 完整备份及恢复仍待验证。

适用环境：Kubernetes / Helm 部署。2026-10-22 已取得客户实际 `neo4j.tgz`，确认 Chart 0.4.14、Neo4j / 镜像 5.26.11；下方新增的 PVC 操作流程仅针对这个已核对的 Bitnami 部署。214 同款测试部署使用 Kubernetes 1.32.8；客户 Kubernetes 和操作系统版本未确认。当前 KK 内嵌的 Chart 5.3.0 / Neo4j 5.26.28 是另一套包，不能混用路径和 values。

本文保留 2026-10-21 的通用配置来源分析及 Helm / ConfigMap 方案，供匹配其他部署方式时参考；当时“未取得实际镜像脚本、未执行导出”等表述仅代表当日证据边界。2026-10-22 的实际包、启动机制、操作与验证以新增补充节为准。

## BK-35 问题与表现

历史安装包没有开启备份所需配置，用户要求手动开启且不能卸载重装。用户反馈直接修改配置文件后，重启又恢复默认配置。本轮没有收到文件路径、启动日志或生效配置输出，也没有连接客户机器。

## BK-35 最终根因或已确认边界

1. 要持久保留设置，应修改生成运行配置的来源。容器内生成的配置文件可能位于临时卷，或者由启动流程根据 ConfigMap / 环境变量重新生成；只修改运行文件不能保证重建后保留。客户具体覆盖链路仍需以其 StatefulSet 的挂载和启动配置确认。
2. Bitnami Chart 0.4.14 的真实模板将 `/opt/bitnami/neo4j/conf` 挂在 `emptyDir` 的 `app-conf-dir` 子路径。`emptyDir` 在 Pod 重建后不保留；同一 Pod 内容器重启是否重新覆盖文件，还取决于镜像启动脚本，本轮未取得该脚本或客户运行证据。
3. 该 Bitnami Chart 的 `apocConfiguration` 生成 ConfigMap 的 `data["apoc.conf"]`；`configuration` 对应 `neo4j.conf`；`existingConfigmap` 非空时，Chart 不生成这份配置，而使用指定的外部 ConfigMap。配置源挂载在 `/bitnami/neo4j/conf`。因此只创建一个未被工作负载引用的 ConfigMap 不会生效。
4. 当前 KK 包使用 `config` 与 `apoc_config`，分别生成 `*-user-config` 和 `*-apoc-config`；后者只有在 `apoc_config` 非空时才生成并挂载。不能将这套 values 直接用于 Bitnami 0.4.14。
5. Neo4j / APOC 5 的 `apoc.export.file.enabled=true` 应放在 `apoc.conf`，不能放在 `neo4j.conf`。关闭 Neo4j 严格配置校验也不会使放错文件的 APOC 设置生效。
6. 当前 Web 实际调用 `apoc.export.cypher.all`，属于在线逻辑导出。备份端口暴露、`/backups` 存储挂载、Web 定时任务、Enterprise 原生在线物理备份是不同事项，不能互相作为启用证据。当前 KK 包的 `services.neo4j.ports.backup.enabled` 不是 APOC 文件导出开关；最终端口还要看渲染后的 Service。

## BK-35 处理方案与手动步骤

以下为待在目标环境执行的步骤，本轮仅提供方案。整个处理不需要 Helm uninstall、删除 StatefulSet 或删除 PVC；配置生效可能需要一次正常重启，单副本会短暂停服。

### 1. 确认实际 Chart 和配置来源

在已选择正确集群上下文的 Master 上执行：

```sh
helm list -n neo4j
kubectl get configmap -n neo4j
kubectl get statefulset neo4j -n neo4j -o jsonpath='{range .spec.template.spec.containers[*]}{"container="}{.name}{"\n"}{range .volumeMounts[*]}{.name}{" -> "}{.mountPath}{"\n"}{end}{end}'
kubectl get statefulset neo4j -n neo4j -o jsonpath='{range .spec.template.spec.volumes[*]}{.name}{" configMap="}{.configMap.name}{"\n"}{end}'
```

名称不同则替换命名空间、release、StatefulSet 名称。当前 KK 还通过 projected volume 引用配置源，需要检查 `.spec.template.spec.volumes[*].projected.sources`；上述直接 ConfigMap 字段为空，不代表没有配置挂载。只记录必要的挂载和配置键，不上传 Secret、完整 values 或客户完整配置。

### 2. 已挂载配置源时，直接修改来源

先确认引用的真实 ConfigMap 名，然后执行 `kubectl edit configmap <实际配置源名称> -n neo4j`，在原有 `data["apoc.conf"]` 中合并下面设置，保留其他有效配置：

```properties
apoc.export.file.enabled=true
```

ConfigMap 的字段形式为：

```yaml
data:
  apoc.conf: |-
    apoc.export.file.enabled=true
```

随后正常滚动重启：

```sh
kubectl rollout restart statefulset/neo4j -n neo4j
kubectl rollout status statefulset/neo4j -n neo4j --timeout=10m
```

以上重启命令以实际更新策略为 `RollingUpdate` 为前提；若为 `OnDelete`，更新模板不会自动替换已有 Pod，应在确认停机窗口后正常删除目标 Pod 让原 StatefulSet 重建，仍然保留原 PVC。

若 ConfigMap 为 Helm 管理，后续还要同步对应部署 values；否则以后的 Helm upgrade / rollback 可能重新写回旧配置。外部 `existingConfigmap` 则维护该外部配置源。

### 3. 尚未挂载 APOC 配置时，使用原 Chart 更新已有 release

Bitnami Chart 0.4.14 且未指定 `existingConfigmap` 时，创建一个覆盖文件 `neo4j-backup-values.yaml`：

```yaml
apocConfiguration: |-
  apoc.export.file.enabled=true
```

已有 `apocConfiguration` 内容时，应先合并原内容；这是完整文件字符串，不能用这一行覆盖其他必要设置。随后使用与现场完全相同的 Chart 包执行：

```sh
helm upgrade neo4j /path/to/original/neo4j.tgz -n neo4j \
  --reuse-values -f neo4j-backup-values.yaml
kubectl rollout status statefulset/neo4j -n neo4j --timeout=10m
```

这里的包路径必须替换为原部署 Chart，不应直接拿当前 KK 内嵌包替换 Bitnami Chart。保留原镜像、现有认证 Secret 和持久化参数；如果此前仅通过 `kubectl set image` 修改过镜像，Helm 保存值可能仍是旧值，要把当前镜像明确并入覆盖值，防止本次 upgrade 改回旧镜像。渲染时只检查本次配置、挂载和重启变化，不输出 Secret。

Bitnami 0.4.14 首次增加配置挂载会改变 Pod 模板并正常滚动；已有挂载时仅更新配置内容不一定重启，因为该模板没有配置 checksum 注解。仅在未自动重建 Pod 时补执行上一节的 `rollout restart`，避免重复重启。指定了 `existingConfigmap` 时应修改外部 ConfigMap，单独设置 `apocConfiguration` 会被忽略。

如果实际使用当前 KK 同类 Chart，覆盖值改为：

```yaml
apoc_config:
  apoc.export.file.enabled: "true"
```

该 Chart 使用配置 checksum 触发滚动。两类 Chart 均需要实际存在且已加载匹配版本的 APOC 插件；在有权限的 Neo4j Browser / Cypher Shell 中执行 `RETURN apoc.version();` 可检查加载状态。若过程或函数不存在，先核对插件 jar、实际插件目录及 allowlist / unrestricted 配置，不能把当前包的 `/var/lib/neo4j/labs` 路径直接套在历史 Bitnami 镜像上。

## BK-35 实际旧包、PVC 加载与完整操作流程（2026-10-22）

### 1. 实际包与故障定位

用户提供的安装命令形式如下，域名脱敏为示例 `neo4j.example.com`，执行时使用实际部署域名：

```sh
helm upgrade --install neo4j ./neo4j.tgz --namespace neo4j --create-namespace \
  --set-string advertisedHost=neo4j.example.com
```

归档阶段重新只读检查本地 `g_web_installer/neo4j.tgz`：大小 52477 字节，SHA-256 为 `63c5ef5b5195cf56948bd1d09bf0f645d084ff895749ad68d512b8195863039e`；包内 `Chart.yaml` 为 0.4.14 / appVersion 5.26.11，镜像为 `registry.digiwincloud.com.cn/bitnami/neo4j:5.26.11`。它是用户提供的独立旧包，不是当前 KK 的内嵌包。

同一会话前段按用户授权在 214 使用该包安装复现，随后检查实际镜像与工作负载，确认：

- `/opt/bitnami/neo4j/labs/apoc-5.26.11-core.jar` 已存在，`/opt/bitnami/neo4j/plugins` 初始为空。APOC 随镜像提供，但默认运行配置没有让 Neo4j 从 labs 目录加载该 JAR。对应导出错误为 `There is no procedure with the name apoc.export.cypher.all registered for this database instance`。
- `/opt/bitnami/neo4j/conf` 是 `emptyDir` 中的运行配置目录，直接在这里编辑不能跨 Pod 重建保留。
- `/bitnami/neo4j` 由 PVC 挂载。该包默认 `configuration`、`apocConfiguration`、`existingConfigmap` 均为空，默认没有额外的 ConfigMap 覆盖 `/bitnami/neo4j/conf` 子目录，因此可以在这里维护 PVC 中的完整配置。
- 实际镜像启动路径经 `entrypoint.sh`、`setup.sh` 调用 `neo4j_initialize`；`/opt/bitnami/scripts/libneo4j.sh` 中存在将 `NEO4J_MOUNTED_CONF_DIR` 内容复制到运行配置目录的逻辑。本次该来源目录为 `/bitnami/neo4j/conf/`，目标为 `/opt/bitnami/neo4j/conf/`。所以 PVC 方案生效依赖已核对的镜像启动逻辑，并非 Helm 或 rollout 自动猜测配置位置。
- `neo4j.conf` 的 allowlist 示例在本次镜像中是注释，手动导出成功时无需额外修改它。不能把带 `#` 的示例行当成生效配置，也不要把其他镜像的限制照搬到本例。

本次需维护两个文件：

| 文件 | PVC 中的保存位置 | 启动后的运行位置 | 本次设置 |
|---|---|---|---|
| neo4j.conf | `/bitnami/neo4j/conf/neo4j.conf` | `/opt/bitnami/neo4j/conf/neo4j.conf` | `server.directories.plugins=/opt/bitnami/neo4j/labs` |
| apoc.conf | `/bitnami/neo4j/conf/apoc.conf` | `/opt/bitnami/neo4j/conf/apoc.conf` | 开启文件导出，并按 Neo4j import 目录解析导出路径 |

若实际部署在 `/bitnami/neo4j/conf` 另挂了 ConfigMap，应使用前文修改真实 ConfigMap / Helm 来源的方案；不能在只读挂载内套用下面的 PVC 写入命令。原包本身不包含镜像启动脚本，不能只读 Chart 就认定任何镜像都具备上述复制行为。

### 2. 主机执行：进入 Neo4j Pod

先确认目标集群上下文、Pod 和原 PVC，再进入 Pod：

```sh
kubectl get pods,pvc -n neo4j
kubectl exec -it -n neo4j neo4j-0 -c neo4j -- sh
```

后面的第 3、4 步在 Pod 内执行。每条命令若报错，应先处理该错误，再执行下一步；不要把步骤编号或 Shell 的 `$` 提示符一起粘贴。

### 3. Pod 内执行：初始化持久配置并修改两个文件

创建目录；仅在 PVC 中尚无同名文件时，从当前运行目录复制完整配置，保留已有定制内容：

```sh
mkdir -p /bitnami/neo4j/conf /bitnami/neo4j/import
[ -f /bitnami/neo4j/conf/neo4j.conf ] || cp /opt/bitnami/neo4j/conf/neo4j.conf /bitnami/neo4j/conf/neo4j.conf
[ -f /bitnami/neo4j/conf/apoc.conf ] || cp /opt/bitnami/neo4j/conf/apoc.conf /bitnami/neo4j/conf/apoc.conf
```

首次初始化也可一次复制两个文件，但无条件执行 `cp` 会覆盖 PVC 中已有的同名配置；已有配置需先留副本。以下 `sed -i.bak` 会在当前文件旁保存本次替换前的 `.bak`，再次执行会更新该备份，不是多版本备份。

修改 PVC 中的 `neo4j.conf`，只替换有效的插件目录设置：

```sh
sed -i.bak '/^[[:space:]]*server\.directories\.plugins[[:space:]]*=/d' /bitnami/neo4j/conf/neo4j.conf
printf '\nserver.directories.plugins=/opt/bitnami/neo4j/labs\n' >> /bitnami/neo4j/conf/neo4j.conf
```

修改 PVC 中的 `apoc.conf`，先删除同名有效设置再追加，避免重复定义：

```sh
sed -i.bak -e '/^[[:space:]]*apoc\.export\.file\.enabled[[:space:]]*=/d' -e '/^[[:space:]]*apoc\.import\.file\.use_neo4j_config[[:space:]]*=/d' /bitnami/neo4j/conf/apoc.conf
printf '\napoc.export.file.enabled=true\napoc.import.file.use_neo4j_config=true\n' >> /bitnami/neo4j/conf/apoc.conf
```

`printf ... >> 文件` 是追加写入，不会打开编辑器。`apoc.export.file.enabled=true` 允许导出文件；`apoc.import.file.use_neo4j_config=true` 让相对文件名按 Neo4j 配置的 import 目录解析。本次 Web 会读取 `server.directories.import` 再取出 `.cypher`，两者必须一致；只允许导出而路径不同，仍可能出现文件找不到。保留原有 `apoc.import.file.enabled` 等其他设置。

### 4. Pod 内执行：两个文件都检查，然后退出

检查插件目录：

```sh
grep -E '^[[:space:]]*server\.directories\.plugins[[:space:]]*=' /bitnami/neo4j/conf/neo4j.conf
```

预期有效设置为：

```properties
server.directories.plugins=/opt/bitnami/neo4j/labs
```

检查 APOC 的两个开关：

```sh
grep -E '^[[:space:]]*apoc\.(export\.file\.enabled|import\.file\.use_neo4j_config)[[:space:]]*=' /bitnami/neo4j/conf/apoc.conf
```

预期每个设置各一条，值均为 true：

```properties
apoc.export.file.enabled=true
apoc.import.file.use_neo4j_config=true
```

上述检查只证明 PVC 文件已保存。执行下面命令回到主机终端，再操作 Kubernetes：

```sh
exit
```

### 5. 主机执行：补模板标签并安排一次滚动更新

本次工作负载为 `StatefulSet/neo4j`，实际旧包默认 `RollingUpdate`。可先检查策略：

```sh
kubectl get statefulset neo4j -n neo4j -o jsonpath='{.spec.updateStrategy.type}{"\n"}'
```

补标签需要修改 Pod 模板，而非只给当前 Pod 打标签：

```sh
kubectl patch statefulset neo4j -n neo4j --type=merge -p '{"spec":{"template":{"metadata":{"labels":{"app":"neo4j"}}}}}'
```

- 返回 `patched` 且实际策略为 `RollingUpdate`：标签变化已触发滚动更新，等待本次更新即可。
- 返回 `patched (no change)`：已有相同标签，不会产生第二个标签，也不会因为重复设置报错；若本次刚修改 PVC 文件，则需要下面这条命令触发配置重新加载。

```sh
kubectl rollout restart statefulset/neo4j -n neo4j
```

不要在标签刚触发更新时无条件紧接着再执行 restart。统一等待更新完成：

```sh
kubectl rollout status statefulset/neo4j -n neo4j --timeout=300s
```

若目标为 `OnDelete` 或更新被分区阻挡，不能按上述输出推定已有 Pod 已替换，应按实际策略安排维护。单副本滚动更新会短暂停服；本流程不执行卸载、不删除 PVC，重建后仍需核对原卷继续绑定。后续 Helm upgrade 时还应同步保留模板标签，直接 patch 不会反写 Helm values。

### 6. 主机执行：确认新 Pod 读取 PVC，并检查运行目录中的两个文件

```sh
kubectl logs -n neo4j neo4j-0 -c neo4j | grep -E 'Copying mounted configuration|Found mounted.*conf'
kubectl get pod -n neo4j -l app=neo4j --show-labels
kubectl get pvc data-neo4j-0 -n neo4j
```

应看到复制挂载配置，以及发现挂载的 `neo4j.conf`、`apoc.conf` 的日志。日志中的 `The general Neo4j configuration will be skipped` / `The APOC plugin configuration will be skipped` 表示跳过自动生成，采用已提供文件，不表示跳过读取配置。

重启前检查 `/bitnami/neo4j/conf`；重启后还要检查实际运行目录 `/opt/bitnami/neo4j/conf`，不能只检查其中一个文件：

```sh
kubectl exec -n neo4j neo4j-0 -c neo4j -- grep -E '^[[:space:]]*server\.directories\.plugins[[:space:]]*=' /opt/bitnami/neo4j/conf/neo4j.conf
kubectl exec -n neo4j neo4j-0 -c neo4j -- grep -E '^[[:space:]]*apoc\.(export\.file\.enabled|import\.file\.use_neo4j_config)[[:space:]]*=' /opt/bitnami/neo4j/conf/apoc.conf
```

预期三项有效配置与第 4 步一致。Pod Running、PVC Bound、配置复制日志均不单独证明导出功能成功。

### 7. 主机执行：进入 Cypher Shell；数据库内验证注册和手动导出

```sh
kubectl exec -it -n neo4j neo4j-0 -c neo4j -- /opt/bitnami/neo4j/bin/cypher-shell -u neo4j -d neo4j
```

在密码提示中输入实际数据库密码，不把密码粘到文档或命令行参数中。进入 Cypher Shell 后，先执行：

```cypher
SHOW PROCEDURES YIELD name WHERE name = 'apoc.export.cypher.all' RETURN name;
```

返回一行过程名后，可以手动导出一次，使用时间戳生成测试文件名：

```cypher
CALL apoc.export.cypher.all('manual-apoc-check-' + toString(timestamp()) + '.cypher', {}) YIELD file RETURN file;
```

这是实际逻辑导出操作，会产生测试 `.cypher` 文件；返回 `file` 且无错误表示本次调用成功。查询以分号结束；执行 `:exit` 退出 Cypher Shell。

### 8. 最后执行 Web 备份验证

先确认 Web 实际读取的集群 `config.yaml` 中存在 Neo4j 组件记录及实际用户名、密码。`app=neo4j` 标签只满足 Pod 筛选条件，不会自动登记 Web 组件，也不会同步数据库密码。凭据及 `Unable to discover Neo4j databases` 的独立根因见 [BK-36](BK-36.md)。

这说明问题已能在直接导出命令中复现，不能仅解释为 Web 未更新代码或后台打包逻辑错误；但仍未证明实际 APOC 调用执行到了哪一步。此前通过的是最小 `sh -s` 与带 `-it` 的配置查询，和本次 `-i`、实际 APOC 导出不是同一对照，不能据此单独断言无 TTY 导出失败或 APOC 本身失败。

下一步保持本次实际导出命令的客户端、数据库、查询及其他参数不变，只将 kubectl exec 的 `-i` 改为 `-it` 进行对照。文件名仍由时间戳生成：

```sh
kubectl exec -it -n neo4j neo4j-0 -c neo4j -- /opt/bitnami/neo4j/bin/cypher-shell -u neo4j -d neo4j "CALL apoc.export.cypher.all('manual-check-' + toString(timestamp()) + '.cypher', {}) YIELD file, nodes, relationships RETURN file, nodes, relationships;"
```

上面归档命令省略密码参数，由交互提示输入实际密码；严格对照执行时应继续使用同一已验证的凭据与其他参数，文档不保存其字面值。该命令实际导出整个 neo4j 数据库，不只是注册查询或目录检查。

若带 TTY 的同一导出返回文件名而无 TTY 失败，才进一步核对执行模式与客户端 / 流式链路差异；若仍失败，则应在已建立的 Cypher Shell 会话内执行同一导出，并结合相应 exec 请求错误及 Neo4j 日志继续区分。不能只根据带 TTY 成功就直接给 Web 的文件传输脚本增加 `-t`：当前实现以标准输出传送 `.cypher` 内容，需另行验证终端换行、标准错误合并及非终端 stdin 等行为。

目前尚无上述 TTY 对照输出或客户导出文件证据。未修改 Web、数据库配置、密码或服务状态，也没有代客户发起导出；Web 完整备份及恢复仍未通过验证。
