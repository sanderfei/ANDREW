# BK-26：备份目录和NFS上传成功后的本地清理

项目：g_web_installer。记录状态：历史功能验证。来源会话起始日期：2026-07-28, 2026-07-29（含之后续问，不是本次现场检查日期）。

适用标签：Kubernetes any；系统 any；安装模式 any。any 表示历史证据未限定，需按实际版本再次核对；不是承诺所有环境兼容。

## BK-26 问题与表现

本地backup/files看不到归档，以为备份没生成；keep_local=false误以为不占本地空间。

## BK-26 最终根因或已确认边界

归档先在Web本地生成，NFS上传成功后按策略删除临时副本。控制记录/history仍在Web数据目录，NFS是文件目的地。

## BK-26 处理方案

按records.json核对storage_type/nfs_path与对应PID末尾日志，再查远端实际文件大小。保留足够本地暂存空间；上传失败必须留文件供恢复。keep_local=false仅指成功后清理，不免除生成阶段空间。

## BK-26 验证证据与限制

历史实际1,732,033,474字节镜像归档在NFS、记录success且本地已删除；NFS多目标部分观察仅基于记录，证据强度不能混同。

以上为历史归档结论，本次仅整理文档，未重新连接客户环境、部署或触发业务操作。

## BK-26 补充：选择 local 时的备份目录（2026-10-21）

适用环境：本地 `g_web_installer` 的 `release` 分支，HEAD `1329551`。本轮只核对后端源码；主机进程和容器部署均按 Web 进程的工作目录计算，未连接现场确认文件。

问题表现：用户询问 Web 备份选择 `local` 后备份文件保存在哪个目录，本轮没有提供备份失败报错。

已确认路径：

```text
<Web 进程启动工作目录>/data/cluster/<集群名>/backup/files/
```

`local` 指 Web 后端运行环境中的文件系统。`GET_DATA_DIR()` 使用 `os.Getwd()` 拼接 `data`；`backupRootDir()` 再拼接 `cluster/<集群名>/backup`，`backupFilesDir()` 最后拼接 `files`。`RunBackup()` 把输出文件名加入该目录；存储目标列表中的 `local.path` 返回同一目录。

可执行查看步骤：

1. 确认 Web 的启动工作目录及备份所属集群名。
2. 在该工作目录执行 `ls -lh data/cluster/<集群名>/backup/files/`，将占位符替换为实际集群名。也可读取 `GET /api/v1/clusters/<集群名>/backups/storage-targets` 响应中的 `local` 目标 `path`。
3. 备份配置和记录在同级 `backup/config.json`、`backup/records.json`，执行日志在 `data/cluster/<集群名>/history/<pid>/`；查具体文件时再与备份记录核对。

按当前 121 发布约定，从 `/root/wfweb/g_web_installer` 启动时，对应目录为 `/root/wfweb/g_web_installer/data/cluster/<集群名>/backup/files/`。这是根据启动目录约定推导，本轮未检查 121 进程。按当前 Dockerfile 默认 `WORKDIR /g_web_installer` 启动时，容器内目录为 `/g_web_installer/data/cluster/<集群名>/backup/files/`，宿主机目录需按实际数据挂载映射确定。
