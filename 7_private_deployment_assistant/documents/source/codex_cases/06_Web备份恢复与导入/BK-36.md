# BK-36：Neo4j数据库发现失败因Web凭据与实际密码不一致

项目：g_web_installer。记录日期：2026-10-22。记录状态：已确认 214 测试环境认证失败，更新 Web 组件密码后同一列库查询成功；完整 Web 备份归档与恢复待验证。

适用环境：214 / 215 测试集群，Kubernetes 1.32.8，用户提供的 Bitnami Chart 0.4.14 / Neo4j 5.26.11，通过 Helm 安装。使用 Web 集群来源备份、`storage_type=local`；实际 Web 数据目录为 `/root/g_web_installer_data`，运行配置位于 `cluster/<实际集群名>/config.yaml`。操作系统版本未在本次取证中确认。本例不代表客户其他环境的密码或默认值相同。

## BK-36 问题与表现

APOC 配置修复并已手动导出后，214 的新 Web 备份任务在选中 Pod 后失败：

```text
Using Neo4j pod: neo4j-0
Unable to discover Neo4j databases
command terminated with exit code 1
```

用户询问是否因为数据库为空。实际检查显示普通数据库 `neo4j` 和 `system` 均 online，普通库节点数为 0；数据库存在与库中没有节点是两件事，空库不会让正常认证的 `SHOW DATABASES` 丢失数据库名称。

## BK-36 最终根因或已确认边界

1. 本次 Web 集群配置最初没有 Neo4j 组件记录；为组件列表识别补入 `name`、`username` 后，密码仍未配置。`getTargetCredential()` 对集群来源读取 `spec.system.components`，密码缺失时沿用目标默认凭据，不会自动读取实际 Kubernetes Secret。
2. 已只读检查失败任务生成脚本使用的凭据，和当时实际 Neo4j Secret 中的密码不一致；仅比较是否一致，没有显示或归档任一密码。以失败任务凭据复现同一列库查询，返回 `The client is unauthorized due to authentication failure.`；实际有效凭据则查询成功。确认本次故障为 Web 备份凭据与运行数据库不一致。
3. `neo4j_list_databases()` 把 `cypher-shell` 的标准错误重定向到 `/dev/null`。认证失败后继续尝试兼容查询及磁盘目录兜底；目录候选只有 `/data/databases`、`/var/lib/neo4j/data/databases`、`/data/data/databases`，未包含本次 Bitnami 实际的 `/bitnami/neo4j/data/databases`，最终只返回泛化的列库失败提示。
4. 隐藏认证错误和缺少实际目录候选使原因难以判断；它们不是“空库不能备份”的证据。主要修复是配置正确凭据，不能靠目录兜底成功就认为后续 APOC 导出也获得了有效认证。
5. Web 组件列表的已安装检测先要求集群配置中登记 Neo4j，再执行 Helm 查询。因此“Helm release 存在，但 Web 显示未安装”和“补记录后仍列库失败”需要分别核对组件记录与密码；补 Pod 标签不会自动配置 Web 凭据。

## BK-36 处理方案

### 1. 确认实际运行的 Web 数据目录和集群配置

本次先按进程工作目录及数据挂载确认，Web 运行目录中的配置与宿主机 `/root/g_web_installer_data/cluster/<实际集群名>/config.yaml` 为同一实际文件。其他部署必须按自身进程与挂载确认，不能改源码目录下一个未被运行服务读取的副本。

在实际集群配置的 `spec.system.components` 中合并或更新 Neo4j 项，保留其他组件及原配置。下面仅展示结构，占位符需由有权限的操作人员替换：

```yaml
spec:
  system:
    components:
      - name: neo4j
        username: neo4j
        password: <实际有效的数据库密码>
```

这不是整个 `config.yaml`，不能用它覆盖完整集群配置。使用既有授权的凭据来源核实实际数据库密码；不从历史聊天寻找密码，不把解码后的 Secret 输出到终端记录、文档或命令行。只有 Secret 中的候选密码经实际登录成功，才能确认与当前数据库一致；已有数据卷的认证状态不一定随新 Secret 自动变化。

本次在用户明确授权后，将已验证有效的密码写入运行服务实际读取的 Neo4j 组件记录，未修改数据库密码本身，未修改其他配置值和文件权限。完成 YAML 解析、配置差异以及运行服务读取路径一致性检查。

### 2. 手动确认数据库可列出

在目标主机进入 Cypher Shell，通过密码提示输入实际密码：

```sh
kubectl exec -it -n neo4j neo4j-0 -c neo4j -- /opt/bitnami/neo4j/bin/cypher-shell -u neo4j -d system
```

进入后执行 Web 使用的列库查询：

```cypher
SHOW DATABASES YIELD name WHERE name <> 'system' RETURN '__GWI_DB__' + name AS name;
```

预期包含 `__GWI_DB__neo4j`，查询成功退出。执行 `:exit` 退出 Cypher Shell。这一步验证数据库凭据和列库能力；Web 配置是否一致仍需核对实际配置，不能仅凭手动登录成功认定 Web 使用了同一密码。

### 3. 新建一次 Web 备份任务

更新配置后，重新点击“立即备份”，让新任务从当前配置生成脚本。旧失败任务保存的脚本仍携带旧凭据，不能重复执行它验证新配置。

检查新任务的 PID 最终日志、备份记录、实际归档文件及 `.cypher` 内容。若仍失败，应按完整错误继续核对 APOC 加载、导出路径、Pod exec 和归档阶段，不能继续简单归因于空库。

APOC 插件与 PVC 配置的完整操作见 [BK-35](BK-35.md)；旧标签筛选问题见 [BK-34](BK-34.md)。本例只记录认证导致列库失败，不合并为这两种根因。

## BK-36 验证结果与遗留事项

- 失败任务的凭据与实际有效凭据不一致；错误凭据查询实际返回认证失败，实际有效凭据能够列出 `neo4j` / `system`，确认根因。
- 用户授权更新配置后，检查确认 Neo4j 密码已配置且与本次有效凭据一致；运行中的 Web 读取到更新文件。检查只输出布尔结果，不保存密码值。
- 使用更新后的 Web 配置凭据执行同一数据库发现查询，退出码为 0，输出包含 `__GWI_DB__neo4j`。这证明配置凭据和数据库发现查询已通过。
- 测试库节点数为 0，不能据此推断生产库没有数据；本轮没有执行生产数据恢复。
- 尚未取得更正凭据后新 Web 任务的成功终态、归档内容和隔离恢复结果。因此整体元数据保持 `unverified`，不将列库成功写成完整备份恢复成功。
- 错误保留、实际 Bitnami 目录候选及凭据缺失提示可作为后续改进建议；本次仅修正运行配置，没有实现或发布这些源码改进。归档阶段只写本地文档、元数据和索引，没有再次修改远端或触发任务。
