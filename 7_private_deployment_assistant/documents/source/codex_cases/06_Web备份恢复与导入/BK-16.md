适用环境：KK 当前本地 `test`（HEAD `b35e7db`）、Web 当前本地 `release`（HEAD `e93910b`），Kubernetes 部署，在线/离线安装均使用内嵌 Chart。镜像为 Neo4j Community `5.26.28`。历史现场为 214/215，Web 曾发布到 121；本轮未连接这些服务器。系统及 Kubernetes 版本仍标 any，引用时须核对实际环境。

## BK-16 问题与表现

历史 Neo4j 服务已 Ready，Web 旧备份仍使用旧 Pod 标签、卷名或目录，用户希望不中断业务备份。2026-10-21 再次确认：曾需要停服务、挂载 PVC 备份的组件是否为 Neo4j，旧版和现版分别是多少，目前是否已经走在线备份。

## BK-16 最终根因或已确认边界

1. 历史路径使用 `app.kubernetes.io/name=neo4j` 查不到实际带 `app=neo4j` 标签的 Pod；写死 `datadir`，而新版实际卷为 `data`、PVC 为 `data-neo4j-0`，且有 `subPathExpr: data`。旧离线实现依赖这些对象和目录，与新版 Chart 不匹配。
2. 旧镜像版本为 `bitnami/neo4j:3.5.28`；当前 KK 实际内嵌包为 `bitnami/neo4j:5.26.28`。Chart 自身的 `version: 5.3.0` 与 `appVersion: 5.26.28` 是不同字段。
3. 当前实现已经改为 APOC 在线逻辑导出。关键是启用 APOC 并更换 Web 备份实现，不能归纳成仅升级版本就自动获得在线备份。Community 的原生离线 dump 与 Enterprise 的在线物理备份仍有区别。
4. 源码确认了备份路径，不证明现场已部署同一版本、定时备份已开启，或有数据的备份恢复已通过。

## BK-16 处理方案与当前实现

已实现：

- KK 由 `cmd/kk/pkg/component/tasks.go:38` 嵌入 `neo4j.tgz`，`ReleaseNeo4jChart` 释放该包，`DeployNeo4j` 执行 Helm 安装。应以实际归档为准，不能只查看同名解压目录。
- 归档内 `neo4j/values.yaml` 设置插件目录 `/var/lib/neo4j/labs`、`dbms.security.procedures.unrestricted=apoc.export.cypher.*` 和 `apoc.export.file.enabled=true`，镜像标签为 `5.26.28`。
- Web `internal/service/backup/local_backup.go:1510` 起保留已注释的旧逻辑：StatefulSet 缩容到 0，helper Pod 挂载原 PVC，执行离线 dump，再恢复副本。
- 当前有效分支位于同文件 `2300` 行起：找到运行中的 Neo4j Pod，通过 Pod 内的 `cypher-shell` 对选中数据库执行 `CALL apoc.export.cypher.all('<文件名>', {})`，读取 `.cypher` 后打包为 `.tar.gz`，清理 Pod 内临时导出文件。该分支不缩容 Neo4j，也不创建挂载原 PVC 的 helper Pod。
- 2026-10-21 补充工具分工：实际导出由 Neo4j 内的 APOC 插件完成；`cypher-shell` 是发起 Cypher 调用的客户端；Web 生成的脚本通过 `kubectl exec -i` 在运行中的 Pod 内调用该客户端，收取导出内容后使用 `tar -czf` 压缩归档。因此目前的备份工具组合为 APOC、Cypher Shell、kubectl 和 tar/gzip，旧 `neo4j-admin dump` 分支仅保留为注释。本次再次核对 `local_backup.go:2352`、`:2358`、`:2383`、`:2396`，没有触发实际备份。
