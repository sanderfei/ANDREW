# BK-39：Milvus备份GC管理地址误选coordinator导致404

日期：2026-10-30。项目：g_web_installer。记录状态：修正后的用户实际手动备份与归档检查通过，目标集合元数据记录 1000 行并包含 binlog，GC 失败告警消失；恢复及还原后逐条一致性待验证。

## 环境与现象

- Web：121，已部署中央 release `0be7ab1`，相关备份实现提交为 `1538dcd`。前置 standalone 兼容问题及此前发布记录见 [BK-38](BK-38.md)。
- 集群：`k8s_test`，控制节点 214；Milvus Chart 16.0.2 / Milvus 2.6.0 分布式部署。
- 本次用户触发任务实际日志显示 `milvus-backup 0.5.15`、Git SHA `3300460434e8f59830fcfeac5cca096ae7624f3b`。项目 Dockerfile 固定值是 0.5.14，不能据 Dockerfile 推定宿主机实际安装版本。
- 用户手动点击立即备份后，工具打印 pause/resume GC 的 `404 page not found` 警告，但随后 `create backup success`，Web 完成归档并显示任务成功。

## 根因与影响

已发布发现代码将 `backup.gcPause.address` 指向 coordinator Pod IP 的 9091 端口。Milvus 2.6.0 实际在 **proxy** 注册 GC HTTP 管理接口，proxy 再向 coordinator 发 RPC；coordinator 的 HTTP 服务有健康接口，不代表它有 GC 管理路由。这是本次新实现选择管理入口的代码错误，与此前 standalone 前置筛选失败属于不同根因。

官方证据：

- [Milvus v2.6.0 proxy/management.go](https://github.com/milvus-io/milvus/blob/v2.6.0/internal/proxy/management.go)：`RegisterMgrRoute` 注册 pause/resume，处理函数调用 `mixCoord.GcControl`。
- [milvus-backup v0.5.15 manage.go](https://github.com/zilliztech/milvus-backup/blob/v0.5.15/internal/client/milvus/manage.go)：仍请求 `/management/datacoord/garbage_collection/pause` 和 `/resume`，不是工具升级改变路径。

本次工具按其警告策略继续执行，因此 404 没有使 create 和 Web 归档失败。GC 暂停保护未成功生效，不能由小任务成功推导大数据或长时间备份的一致性保障。

## 现场证据

1. coordinator 当前为 `10.233.84.98:9091`；proxy Service 为 `10.233.29.46:9091`。
2. 在确认路由语义后，用纯查询接口 `GET http://10.233.29.46:9091/management/querycoord/node/list` 验证，返回可解析 JSON、字段 `nodeInfos`，证明访问到了 proxy 管理路由；不把这个查询写成 pause/resume 成功验证。
3. 最初错误使用 `OPTIONS` 探测管理路径：coordinator 两个 GC 路径均 404；proxy pause 返回 500，resume 返回 200。官方 handler 没有 HTTP method guard，因此该探测不能视为只读，resume 请求会调用 GC 恢复 RPC；本轮不再调用 GC 控制路径。pause 的 500 不证明暂停成功，也没有执行新备份或数据恢复。

## 本地修正

`internal/service/backup/milvus_discovery.go` 改为从已选 proxy 的 Service 解析实际 HTTP 管理端口，生成 `http://<proxy Service ClusterIP>:<HTTP Service port>`；移除 coordinator Pod IP 作为管理 HTTP 地址的错误选择。缺失 proxy HTTP 端口时明确报错。

该现场对应地址为 `http://10.233.29.46:9091`，仍由工具负责备份期间的 pause/resume，不额外人工调用控制接口，也不以关闭 GC 保护来隐藏警告。

针对性临时测试验证：HTTP Service 端口 9191 映射 container 9091 时必须生成 proxy Service 的 9191；不依赖 coordinator Pod 的 HTTP 路由；缺少 HTTP 端口必须失败。
