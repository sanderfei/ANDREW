# BK-45：214 Milvus 服务异常阻碍新旧备份兼容验证

记录日期：2026-11-13。环境：214 测试 Kubernetes 集群，Helm release 和命名空间均为 `milvus`；初查时 Helm Chart `16.0.2`、app version `2.6.0`、status 为 `deployed`。状态：原组件异常的完整根因未确认；新版与旧版立即备份均有任务及归档证据，修复后定时触发和恢复待验证。

## 问题表现

用户要求安装 KK 中新旧两版 Milvus 并分别通过 Web 立即备份接口验证。准备验证时，只读检查发现 214 已有 Milvus release，etcd、proxy、coordinator 等 Pod 存在 `CrashLoopBackOff`。Helm `deployed` 只表示 Helm release 状态，不能证明组件可用或备份可执行。

初查时 PVC `data-milvus-etcd-0`、`milvus-minio` 为 Bound，其对应 PV 回收策略为 Delete。用户随后明确说明 214 为测试环境、现有数据可清除，并要求先验证新版、再卸载安装旧版；实际操作和结果见下文。

## 已确认边界和证据

etcd 上次容器终止原因为 `OOMKilled`，退出码 137；日志包含恢复 WAL 的内容。这些现象尚不足以确定组件反复退出的完整根因，不能据此断定 WAL 损坏，也不能证明提高内存即可恢复。proxy 和 coordinator 的故障是否由 etcd 引发也仍待核实。

Web 提交 `fdbcbaa` 已实现优先识别 Milvus standalone 并选择历史备份流程，否则选择当前分布式备份流程。立即备份处理器及定时调度器均调用 `internal/service/backup/local_backup.go` 的 `RunBackup`，所以源码层面共用新旧版本选择；立即备份成功也不能单独证明 cron 到点触发成功。中央合并提交 `6e7ee16` 已包含该变更。旧版客户现场背景见 [BK-44](BK-44.md)。

当前源码以 `milvus` 命名空间发现部署，同命名空间内同时存在符合条件的 standalone 与新版 proxy 时会优先选旧版；两次分别验证需具有可区分的隔离目标或经确认的分时方案。未经数据所有者明确授权时，必须保留既有 release、PVC 和业务数据，不能将卸载或 PVC 清理作为默认步骤。

## 后续排查与验证

先在已确认的 214 集群上下文只读核对状态、重启及卷映射：

```bash
kubectl config current-context
helm status milvus -n milvus
kubectl get pods,pvc -n milvus -o wide
kubectl describe pod -n milvus milvus-etcd-0
kubectl logs -n milvus milvus-etcd-0 --previous --tail=100
kubectl get pv
```

根据实际 Pod 名确认日志对象，并结合资源限制、节点内存及事件定位 OOM；如容器重新启动或其他 Pod 有不同失败原因，需分别检查。收集时避免保存凭据和完整配置。

确认现有数据和可恢复备份后，选择不影响现有 release 与 PVC 的隔离验证环境或经明确确认的分时方式。分别验证旧版和新版的数据库数据准备、立即备份任务最终状态、归档内容与恢复；需要证明定时功能时，另外检查真实 cron 到点触发的任务终态。不要将历史其他批次的备份成功代替本轮验证。

## 验证结果与遗留事项

### 2026-11-13 分时安装与立即备份实测

用户授权清除 214 测试数据后，按 KK 对应的 Helm Chart 和安装方式先安装新版；使用 Chart `16.0.2` / Milvus `2.6.0`。121 Web 通过立即备份接口发起任务 `2026-11-12_22-18-36.519_backup_milvus`，最终状态为 `success`。检查备份归档时，看到两行测试数据对应的 segment 元数据及 5 个非空 binlog 文件；没有执行隔离恢复，归档检查不等于恢复能力验证。

随后卸载新版并清理本次测试 PVC，再安装 KK 历史 Chart `4.2.47` / Milvus `2.5.10`。旧版 standalone、etcd 与 MinIO 均达到 Ready。旧版立即备份任务 `2026-11-12_23-23-32.774_backup_milvus` 最终状态为 `failed`，错误为 gRPC `Unauthenticated`。这证明旧版流程已被触发，但不能据此断定具体认证失败原因或备份可用。旧任务生成的含凭据脚本和 Pod 内临时配置已清理；不在本案例保存凭据或相关文件内容。

### 后续旧版认证调整及凭据保护

经用户授权，测试账号按 KK 当前默认配置对齐，旧版接口认证随后成功；不记录实际凭据。用户授权调整旧版凭据处理并重新发布，提交 `52e2333` 经中央合并 `e4b00e9` 进入 release；121 已完成编译、替换与启动。旧版认证信息经标准输入传递，Pod 配置文件仅在可写 tmpfs `/dev/shm` 内临时使用并清理；备份工具调用及原 MinIO 打包流程保留。

旧版写入 2 行测试数据后，立即备份任务 `2026-11-13_00-10-06.712_backup_milvus` 最终为 `success`，备份文件 4210 字节。归档里的 `full_meta` 等成员实际为 MinIO 目录中的 `xl.meta`：其中 `full_meta` 包含测试 collection 和 2 行的元数据，5 个 `insert_log` 对应的 `xl.meta` 含内嵌 Parquet；在内存中读取后，5 个字段各有 2 行，主键和 float32 向量与测试插入一致。这个证据证明归档包含测试数据，但 `xl.meta` 不等同于标准对象归档，也不能证明恢复可用。

### 旧版标准对象归档修复与实测

针对上述物理 `xl.meta` 归档问题，用户授权调整旧版导出方式：Web 提交 `bb8280e` 保留旧版备份生成方式，改为通过 MinIO 对象接口导出备份前缀并生成归档。中央合并 `2b5e88d` 后，121 编译、替换并启动成功，启动 PID 为 `1465203`。

214 的 Milvus 2.5.10 立即备份任务 `2026-11-13_01-32-25.361_backup_milvus` 最终为 `success`，归档大小为 2107 字节。检查确认归档含 5 个标准 JSON 元数据文件和 5 个普通 insert binlog 文件，没有 `xl.meta`；2 条主键和 float32 向量与测试插入数据一致。凭据临时配置已清理。

新版及旧版均已取得立即备份终态和各自归档内容证据。已有定时备份成功记录发生在本次对象导出修复发布前，不能作为修复后定时实际触发的证据。两版本恢复、修复后的定时触发及客户现场结果仍未验证；`verification_status` 保持 `unverified`。
