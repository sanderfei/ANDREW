## BK-23 问题与表现

ERROR1046 No database selected，或暂存导入SQL可能写回业务库。

## BK-23 最终根因或已确认边界

prepare只改CREATE DATABASE/USE到__gwi_b_临时库，不改table名和所有完全限定database.table引用。

## BK-23 处理方案

无CREATE DATABASE/USE的单库SQL可加暂存上下文；含CREATE DATABASE必须有匹配USE。CREATE TABLE demo.users等限定引用应拒绝/审核，USE临时库不能重定向它。生成计划前先确认备份有效。

## BK-23 2026-10-29 源码复核：四接口流程与恢复范围

记录日期：2026-10-29。环境：本地 `g_web_installer` 的 `release` 工作区，HEAD `934701b`；本轮只核对后端源码，未运行测试、构建、真实 HTTP 或远端数据库操作。部署中的二进制及 MariaDB/Atlas 版本未核实，以下为当前源码行为。

本轮问题是澄清 `prepare`、`plan`、`apply`、`restore` 的职责，未反馈新的运行时报错。设 A 为 prepare 时数据库实例中可见的全部非系统且非 `__gwi_b_` 前缀业务库，B 为安装包所定义的目标库集合。

| 接口（共同前缀 `/api/v1/clusters/:cluster/mariadb/schema-sync`） | 当前实现 |
|---|---|
| `POST /prepare` | 读取运行目录下 `data/cluster/<cluster>/mariadb_data.zip`，检查 MariaDB 组件、依赖命令和包内 SQL；备份 A 的结构与数据为 `a_backup.sql.gz`，将 B 导入同一 MariaDB 实例的 `__gwi_b_<库名>` 临时库，再逐个 B 库生成 A → B 的结构差异 SQL，完成后清理临时库。 |
| `GET /:pid/plan` | 检查 prepare 已完成及备份、库清单、计划文件等产物存在，下载服务器保存的 `schema_update.sql`，不执行 SQL。 |
| `POST /:pid/apply` | 检查 prepare 产物及执行状态，校验备份 gzip 后，用 mysql 直接执行服务器上的计划文件；不重新计算差异，不校验 prepare 后的结构漂移，不把 B 中的数据行导入业务库。 |
| `POST /:pid/restore` | 必须已有 `apply.started`，可用于成功执行后或执行中途失败后的恢复；先删除 A 与 B 并集中的业务库，再导入 prepare 时的 A 全量备份，并清理 B 临时库。B 独有的新库因此被删除；恢复也会覆盖这些库在备份后写入的数据。 |

四个接口归属带 JWT 校验的 `/api/v1` 路由组。四个 handler 都只读取路径参数，无业务 JSON 请求体。三个 POST 返回各自的异步任务 `pid`；HTTP 成功仅表示任务已启动，实际结果还需核对对应任务日志和最终数据。`plan`、`apply`、`restore` 路径中的 `pid` 始终使用 **prepare 返回的 PID**，不能改成 apply/restore 新返回的执行 PID。prepare 产物位于 `data/cluster/<cluster>/history/<prepare_pid>/`。各执行任务的日志可通过 WebSocket `/api/v1/logs/cluster/<cluster>/tail/<执行pid>/execute.log` 读取；需满足 JWT 校验和 WebSocket Upgrade。

### 包约定与差异范围

1. 包内每个 SQL 文件按文件名识别目标库名：反复剥离 `.sql` 后缀，再去掉末尾 `-数字.数字...` 版本段；支持合法连字符库名，不是从任意多库 SQL 内容自动推断所有库。SQL 中显式的库声明须与识别结果一致。
2. 暂存时过滤 `DROP DATABASE/SCHEMA`，将匹配的 `CREATE/ALTER DATABASE/SCHEMA` 和 `USE` 的带反引号库标识符改为临时库；含 `CREATE DATABASE` 却没有匹配 `USE` 会直接失败。没有 `CREATE DATABASE` 时补建临时库及 `USE`。
3. 表名不重命名，完全限定的 `database.table` 引用没有通用重写。不能据此声称任意输入 SQL 都隔离在临时库；使用前应审核此类引用及预期库上下文。
4. 只遍历 B 的库生成计划；A 中未出现在 B 的库不产生删除计划。B 独有库从空临时库比较，计划先建库再建表。库默认字符集/排序规则由脚本单独处理，表、列、索引和约束等交给 Atlas。
5. Atlas 配置跳过删除 schema、表、列，并跳过 Atlas 自身的 schema 修改；这不代表所有其他 ALTER 都无损。计划使用 SQL-only 格式，既有 no-change 文本问题见 BK-22。
6. B 暂存导入使用 `mysql --force`，非零退出只记录 warning，不直接停止 prepare；应检查 `b_import_warnings.log` 并审核计划，不能用 `prepare.done` 证明 B 数据和结构完整导入。

### 先上传数据包（2026-10-29 后续问答）

实际上传入口是 **`POST /api/v1/files/:cluster`**，走 JWT 校验。`UploadFile` 上方的 `/api/v1/upload/:cluster` 是旧注释，不能当作当前路由。请求使用 `multipart/form-data`，必填字段为 `filename=mariadb_data.zip` 和文件字段 `file`。

整包上传示例（占位服务地址、集群名及 JWT；未在本轮实际调用）：

```bash
curl -X POST 'http://<WEB_HOST>:8080/api/v1/files/<cluster>' \
  -H 'Authorization: Bearer <JWT>' \
  -F 'filename=mariadb_data.zip' \
  -F 'file=@./mariadb_data.zip'
```

不填 `chunk_index`、`total_chunks` 即直接保存完整文件到 `data/cluster/<cluster>/mariadb_data.zip`，成功响应的 data 为 `{"merged":true,"received":1,"total":1}`。**本流程必须省略 `task_id`**，否则文件会落在 `data/cluster/<cluster>/task/<task_id>/`，prepare 不会读取该位置。`is_upload_obs` 省略或设为 `0` 即可。

若采用分片上传，每片仍使用相同的 `filename`、`file` 字段，并同时传 `chunk_index` 与 `total_chunks`，序号约定为 `1..total_chunks`；最终响应 `merged=true` 才表示完整文件已合并。上传成功只证明文件保存/分片合并完成，SQL 包约定仍由后续 prepare 检查；本轮没有真实上传 HTTP 验证。

### 任务状态与操作步骤

1. 先通过 `POST /api/v1/files/:cluster` 上传匹配上述约定的 `mariadb_data.zip`（不填 `task_id`），确认 `merged=true` 后调用 prepare，保留返回的 prepare PID；等待任务完成并检查备份、`prepare.done`、警告日志与计划文件。
2. 用 prepare PID 下载并审核计划。apply 执行服务器原文件；修改已下载的本地副本不会改变服务器的待执行计划。
3. 确认实际变更及业务写入安排后调用 apply；同一集群的 prepare/apply/restore 共用非阻塞文件锁，串行执行。执行前写 `apply.started`，成功后写 `apply.done`。
4. 只要 `apply.started` 已存在，原计划就拒绝再次 apply；失败时不会自动回滚。当前错误提示要求先 restore A，再 prepare 新方案。restore 本身成功后写 `restore.done`，再次恢复同一方案会被拒绝。
5. 如需恢复，仍以 prepare PID 调用 restore。恢复先删除 A∪B，不是反向执行 DDL，必须接受备份后数据被覆盖的结果。恢复脚本只在导入后检查 A 库是否存在，没有逐表/逐行完整性核验；完整恢复仍需单独验证。
