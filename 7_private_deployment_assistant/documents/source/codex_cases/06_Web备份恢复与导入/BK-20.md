## 2026-10-29 补充：当前 Web PostgreSQL 导入调用链与失败边界

记录日期：2026-10-29。适用环境：本地 `g_web_installer` 的 `release/290fd15` 后端源码；Web 可运行于宿主机或容器，导入客户端必须安装在实际运行 Web 的环境内。在线/离线集群共用此导入分支。本轮只读核对源码，未连接现场、上传数据或运行数据库命令；历史功能验证不代表该提交在当前现场已验证。

### 问题描述与已确认结论

用户询问 Web 中 PostgreSQL 数据导入逻辑。本轮没有提供新的运行报错；目标是确认入口、文件与数据库映射、连接位置、pgvector 处理、事务及异步结果的边界，不新增故障根因。

当前 V2 入口是 `POST /api/v1/clusters/import/v2`，JSON 为 `{"cluster":"目标集群","database":"postgresql"}`。调用链为：

```text
handler.ImpDataV2
  -> importdata.ImpDataJobV2
  -> validateComponentInstalled
  -> doCommandV2
  -> importPostgresqlV2
  -> command.Execute.Exec
     -> PreExec: makePostgresqlImportScriptV2
     -> 在 Web 本机启动 /bin/bash import_postgresql.sh
     -> 返回任务 PID，后台等待命令退出并写 execute.log
```

`validateComponentInstalled` 先确认组件存在于集群配置，再通过 SSH 检查 Helm release 和 PostgreSQL 命名空间内 Pod 健康。SSH 仅用于这个安装/状态前置检查；真正数据恢复由 Web 环境内的 PostgreSQL 客户端直连数据库。

### 数据包和目标连接

V2 固定读取 Web 工作目录下 `data/cluster/<cluster>/postgresql_data.zip`。ZIP 可包含多个数据库，但有效文件必须直接位于根目录：

```text
postgresql_data.zip
├── app_db.dump
├── analytics.backup
└── vector_db.sql
```

去掉最后一个扩展名就是目标库名，例如 `app_db.dump` 导入 `app_db`，不是从 dump 内部读取目标库名。允许 `.dump`、`.backup` 和 `.sql`；前两者必须具有 `PGDMP` 文件头。拒绝空文件、非普通文件、嵌套路径、非法库名、同一库对应多个文件和其他文件类型。目录条目会被跳过；因此根目录放文件即可，不要多包一层目录或附带 README 等文件。

连接参数取自集群 `config.yaml`：第一个 `control-plane` 节点的 `Address` 作为目标地址，端口固定 `30432`，不读取组件自定义端口。账号来自 `postgresql` 组件的 `UserName`，为空时用 `postgres`；密码必须在组件配置中存在。用户名和密码不能包含换行或 NUL，经 stdin 传入 Bash，密码导出为 `PGPASSWORD`，不写入脚本和命令参数。

### 脚本执行顺序

1. 检查 Web 环境内存在 `unzip`、`find`、`sort`、`psql`、`pg_restore`。脚本要求 `psql` 主版本为 17；只对 `psql --version` 做主版本判断，未独立检查 `pg_restore` 主版本。Dockerfile 安装 `postgresql-client-17`，宿主机直接启动 Web 时仍需自行提供这些命令。
2. 设置 `PGCONNECT_TIMEOUT=10`，连接维护库 `postgres` 执行 `SELECT 1`。没有 `pg_isready` 等待循环，也没有连接失败自动重试。
3. 解压到临时目录，按文件名排序串行处理；退出时清理解压目录并取消 `PGPASSWORD` 环境变量。
4. 根据文件名检查目标库是否存在；不存在时 `CREATE DATABASE`，已存在时直接继续，不主动删库或清空对象。
5. 导入前运行 `ensure_pgvector`：查询 `pg_available_extensions`，要求 `vector` 可用；执行 `CREATE EXTENSION IF NOT EXISTS vector` 和 `ALTER EXTENSION vector UPDATE`，检查已安装版本等于可用的 `default_version`。即使导入内容没有向量表，也会执行这一步；服务器镜像中缺少 vector 扩展文件时导入失败。
6. `.dump`/`.backup` 使用 `pg_restore --exit-on-error --single-transaction --no-owner --no-privileges`；`.sql` 使用 `psql -X --set=ON_ERROR_STOP=1 --single-transaction --file ...`。前者忽略 dump 的 owner 和权限恢复；SQL 文件没有对应的自动过滤或改写。
7. 导入后再次运行 `ensure_pgvector`；所有文件处理完成后打印总导入库数。

脚本使用 `set -Eeuo pipefail`，数据库命令失败会使任务失败。当前没有 `--clean`、清库、通用 UPSERT、自动跳过已有表或失败自动恢复逻辑：重放到非空库可能因同名表、索引或数据冲突失败。每个文件的恢复命令使用单事务；建库和导入前后的扩展操作在该事务之外，多库之间也没有统一事务。因此后一个库失败不会回滚前面已完成的库；导入后扩展检查失败时，导入事务可能已经提交。SQL 若自行包含事务控制或跨库命令，应按文件实际语句另行判断，不能仅凭 `--single-transaction` 承诺任意 SQL 的原子恢复。

### 异步完成与 V3 复用

V2 返回的 `pid` 是任务标识，不是数据库导入完成。日志位于 `data/cluster/<cluster>/history/<pid>/execute.log`（默认数据目录），任务结束时依据命令退出状态输出成功或失败，并在成功时记录成功任务。日志接口为 `GET /api/v1/logs/cluster/<cluster>/tail/<pid>/execute.log`。退出码为 0 说明当前导入脚本完成，没有额外核对业务行数、查询结果或向量索引使用情况。执行器虽然调用 `LockOwner`，当前 `lock_owner.go` 的 `Flock` 被注释，不能据此承诺同一集群导入互斥。

V3 OBS 版本导入调用 `PrepareArchiveImport` 时，先复制并校验私有归档，随后复用 `makePostgresqlImportScriptV2`。其 `ArchiveImport.Run` 同步等待脚本完成，输出并入上层任务日志，失败向上传递；不为 PostgreSQL 再创建独立任务 PID。V3 可以使用调用方给定的包路径，不要求外层归档文件名固定为 `postgresql_data.zip`，内部文件规则和数据库执行逻辑相同。

1. 准备上面结构的 ZIP，确认 Web 环境客户端及目标 `vector` 扩展可用、节点 `30432` 可达，组件配置与实际账号密码一致。

这份项目说明属于对实现和打包用法的整理，文档与代码只能证明当前行为，不能作为用户原始需求或这些限制合理性的独立证据。本轮尚未逐条核对原始需求，不能把 ZIP 根目录、文件名去后缀映射目标库等限制记作用户明确要求，也不能仅凭 Git author 确认实际执笔者。

| 事项 | PostgreSQL 17 原生行为 | 当前 Web 协议 |
|---|---|---|
| 单库导出 | `pg_dump` 一次导出一个库，输出文件名可由 `-f` 自行指定 | 去掉最后扩展名作为目标库名 |
| 输出格式 | plain SQL（`-Fp`）、custom（`-Fc`）、directory（`-Fd`）、tar（`-Ft`） | 外层必须 ZIP，内层只接受 `.sql` 与具有 `PGDMP` 头的 `.dump`/`.backup` |
| 目录层级 | directory 格式本身就是目录，原生工具不要求额外 ZIP 根目录结构 | 有效文件必须直接位于 ZIP 根目录 |
| 归档恢复目标 | `pg_restore -d` 指定目标；使用 `--create` 时按归档内库名创建/恢复 | 不传 `--create`，使用文件名推导的 `--dbname` |
| 多库导出 | `pg_dumpall` 可生成含多个库及全局对象的 SQL 脚本 | 约定一个文件对应一个库，不保证兼容整集群 SQL |

格式与单库/多库行为见 [PostgreSQL 17 pg_dump](https://www.postgresql.org/docs/17/app-pgdump.html)、[pg_restore](https://www.postgresql.org/docs/17/app-pgrestore.html)、[pg_dumpall](https://www.postgresql.org/docs/17/app-pg-dumpall.html)。文件扩展名本身不决定原生归档格式；`PGDMP` 是当前 custom 分支的识别条件，不能称为所有 PostgreSQL 备份的统一文件头。

例如导出源库 `source_db` 时，可执行 `pg_dump -Fc -d source_db -f snapshot.dump`；原生恢复也可以用 `pg_restore -d target_db snapshot.dump`。当前 Web 若要导入 `target_db`，则需把该 custom 文件命名为 `target_db.dump`，再按约定放入 ZIP。对于 SQL 文件，重命名不会改写内部的 `CREATE DATABASE`、`\connect` 或其他显式数据库引用；不能承诺任意 SQL 都会因此恢复到文件名指定的库。

本轮 Web 后端范围未发现 `pg_dump`/`pg_dumpall` 导出实现，本地备份目标列表也不含 PostgreSQL（`internal/service/backup/local_backup.go:80`）。现有“下载 PostgreSQL 数据”路径只是向上游 private-service 的 `/api/v1/privatization/download/data` 发 HTTP POST，并将响应保存为 `postgresql_data.zip`（`internal/transport/handler/download.go:50`、`internal/constants/constants.go:91`、`pkg/utils/downloader.go:40`）。尚未检查上游实际包生成逻辑，不能因此断言整个系统没有 PostgreSQL 导出，也不能把当前 Web 输入协议描述成已经统一实现的导出协议。

拒绝路径穿越、非普通文件等校验有独立意义，应继续保留；正常的嵌套目录不是路径穿越。若以后扩大兼容性，可考虑用 manifest 或显式参数映射文件与目标库、检测实际格式，并将安全路径检查与“只能根目录”的打包约束分开。这些是建议，本轮未实现、未发布，也未运行导出恢复验证。

## 2026-10-29 后续证据：用户实际导出脚本与 Web 目录层级匹配

| 位置 | 示例 | 对当前流程的含义 |
|---|---|---|
| ZIP 内成员路径 | `app_db.dump` | 当前 Web 要求的根层文件 |

| Web 保存原 ZIP 的宿主位置 | `data/cluster/<cluster>/postgresql_data.zip` | 导入器读取原包的位置，与 ZIP 成员路径无关 |

## 2026-10-29 实现更新与 214 原生多库导出恢复验证

## 2026-11-02 客户 custom 归档建库失败：locale 与原库名边界

### 用户澄清的需求与两条分支的范围

用户原话为“目前需求是 用我们的导出脚本导出后再通过web导入”，当前需求聚焦 `docs/export_postgresql.sh` 原包的导出和导入，未要求移除或禁止其他格式。该 Bash 脚本通过 `pg_dumpall -h` 连接本机或远程 PostgreSQL，原样输出 ZIP 只有 `postgresql.sql`，走 Web SQL/`psql` 分支。截图成员是 `digispace.dump`，走 custom/`pg_restore` 分支，因此不是该脚本原样输出；截图不能证明其实际导出来源，也没有证明脚本 SQL 分支已经复现相同问题。

脚本运行于 Linux 不保证源端数据库具有 Linux locale：SQL 中 locale 来自所连接的源 PostgreSQL 服务端数据库定义，源端可以是远程 Windows；不同 Linux 环境也可能存在 locale 差异。以上是兼容性边界，本轮没有运行或复现脚本跨平台导出恢复。

PostgreSQL 17 `pg_dumpall` 源码的默认行为（不带 `--clean`）对 `postgres`、`template1` 使用连接已有目标同名库后导入内容，不执行截图中的 `CREATE DATABASE postgres`；因此下述 custom 同名建库冲突不适用于该脚本 SQL 分支。内置库内容仍可能与目标已有对象冲突，普通业务库也仍携带源 locale 建库，不能据此承诺任意环境都可恢复。依据为 PostgreSQL `REL_17_STABLE/src/bin/pg_dump/pg_dumpall.c` 的数据库导出分支，本轮只读代码及官方资料，没有实施优化。

### 问题表现与截图证据（仅 custom 分支）

用户提供真实 Web PostgreSQL V2 导入失败截图。包成员为 `pgsql_20261102/digispace.dump`，连接 `192.168.10.254:30432` 成功，custom 归档进入 `pg_restore --create` 分支后执行：

```sql
CREATE DATABASE postgres WITH TEMPLATE = template0
    ENCODING = 'UTF8'
    LOCALE_PROVIDER = libc
    LOCALE = 'Chinese (Simplified)_China.936';
```

服务器返回 `invalid LC_COLLATE locale name`，任务 `exit status 1`。本轮没有连接或操作该用户目标集群，没有查询其 Pod/操作系统或原库数据；现场结论限于截图中的实际错误和本地源码核对。

### 已确认原因与后续冲突边界

1. 直接失败点是数据库服务端不接受归档指定的 locale，发生在建库阶段。网络连接已成功，不能把本次报错归因于 ZIP 嵌套目录或客户端未安装；也不能据此认定表、数据已经恢复。
2. `Chinese (Simplified)_China.936` 呈 Windows 风格。源端 Windows、目标端其他系统的 locale 差异是可能解释，但源端与目标操作系统未直接核实，不能记为已证实事实。`ENCODING='UTF8'` 与 locale 名是不同设置，不能仅凭 `.936` 断言归档数据是 GBK 编码。
3. SQL 明确写 `CREATE DATABASE postgres`，说明归档记录的原数据库名为 `postgres`。成员文件叫 `digispace.dump` 不代表库名是 `digispace`，重命名文件也不会改变当前 `--create` 的目标。
4. 当前 Web 先用 `--dbname postgres` 连接维护库并执行 `SELECT 1`，custom 随后固定 `pg_restore --create --exit-on-error --no-owner --no-privileges --dbname postgres`。这里 `--dbname postgres` 是 `--create` 模式的初始连接库，真正恢复目标仍由归档内建库定义决定。既然维护库连接已成功，目标 `postgres` 已存在；即使解决 locale，继续按原库名创建还会遇到同名冲突，当前不能保证重试成功。

本次不是建议清理目标库的依据。不要为本归档删除现有 `postgres`，也不要用 `--clean` 绕过同名冲突。

### 截图 custom 归档的手动处理方向（不属于本次脚本原包支持需求，尚未实施）

以下仅针对已确认的截图 custom 分支，不能作为脚本 SQL 分支必须新增的流程。先确认实际导出的是哪一个源数据库、归档是否包含预期业务数据，以及希望恢复到的独立目标库名。然后在数据库服务端实际运行环境检查 locale；Web 客户端或 Kubernetes 宿主机上的 locale 列表不能替代数据库 Pod 的环境。

例如在实际 PostgreSQL Pod 内检查可用 locale（镜像提供 `locale` 命令时）：

```bash
kubectl -n '<数据库命名空间>' exec '<PostgreSQL Pod>' -- locale -a
```

数据库目录属性可在已授权连接中查询：

```sql
SELECT datname, pg_encoding_to_char(encoding) AS encoding,
       datcollate, datctype
FROM pg_database
WHERE datname IN ('postgres', 'template0');
```

若业务确认可以采用服务端支持且合适的 UTF8 locale，先创建一个新的空库，例如 `restore_target`。下列 locale 占位值必须先替换成服务端已核实的值，不能直接照抄，也不能默认 `C.UTF-8` 或 `en_US.UTF-8` 一定存在或等价于原中文排序规则：

```sql
CREATE DATABASE restore_target WITH TEMPLATE = template0
    ENCODING = 'UTF8'
    LOCALE_PROVIDER = libc
    LC_COLLATE = '<服务端已确认的UTF8_locale>'
    LC_CTYPE = '<服务端已确认的UTF8_locale>';
```

在新空库中恢复 custom 内容时不带 `--create`，用 `-d` 明确目标库；连接凭据由执行人员当次提供，不写入命令或本案例：

```bash
pg_restore --exit-on-error --no-owner --no-privileges \
  -h '<数据库地址>' -p '<端口>' -U '<授权账号>' \
  -d restore_target '<已提取的custom归档路径>'
```

这是手动指定目标库的方案方向，**当前 Web 固定 `--create`，尚不支持通过该界面/API走上述流程**；本轮未修改代码，也未在用户现场执行建库、恢复或删除。原归档若还显式依赖特定 collation、扩展、角色或其他对象，仍需分别核对。更换 locale 可能改变排序、大小写比较以及唯一约束行为，不能只以“可以建库”作为业务等价的证明。
