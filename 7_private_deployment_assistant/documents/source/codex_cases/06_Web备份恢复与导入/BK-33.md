## BK-33 问题与表现

用户先询问 StarRocks 数据导入是否可以使用 MySQL dump，随后询问适合低频、少量数据的导入导出工具，最后继续确认 mysqldump 能否完成。结合后续上下文，按 StarRocks 自身表结构和数据导出、再恢复到 StarRocks 的需求进一步核对；这与将 MySQL 原始 InnoDB dump 迁入 StarRocks 是两个不同场景。需要区分 mysqldump 导出工具、mysql 客户端执行 SQL、可视化数据传输，以及 StarRocks 的批量数据导入接口。不能因为支持 MySQL 协议，就推断完整 MySQL 备份可原样恢复。

## BK-33 最终根因或已确认边界

- mysqldump 负责导出；SQL 文件通常由 mysql 客户端读取后发送给目标数据库执行。MySQL 官方文档说明 dump 可以包含建表、插入、会话设置及锁表等语句。
- StarRocks 3.5 支持 INSERT INTO VALUES，包括一次插入多行；官方将这种方式定位为少量数据/功能演示，不建议作为海量或高频生产导入方式。
- StarRocks 有自己的建表和表模型语法。其 CREATE TABLE 支持的引擎列表不包含 InnoDB；MySQL dump 中的 ENGINE=InnoDB 建表定义不能直接照搬，字段类型、键模型、分区/分桶等也需按目标表设计适配。
- 根据两者官方文档可以得出：原始 dump 的建表及其他 MySQL 特定语句需逐项核对，不能承诺整份 SQL 直接兼容。这是基于文档的兼容性判断，本轮没有执行 dump 或重放文件，也不将所有 INSERT 判定为不可用。
- Stream Load 接收 CSV/JSON 数据，不把 mysqldump 的 SQL 脚本作为数据文件执行。

## BK-33 处理方案

若手头是 MySQL 导出的 SQL 文件且数据量很小：先按 StarRocks 语法创建目标库和表，再生成或整理为目标版本兼容的 INSERT 语句，明确列名、字段类型和转义规则。不能仅通过逐行 grep INSERT 可靠转换通用 dump，多行语句及字符串内容需要按 SQL 结构处理。移除或适配 MySQL 特定 DDL/会话/锁表语句后，先在隔离的目标测试表验证。

以下是待用户填入参数的执行模板，本轮未执行；输入文件必须已审查为兼容目标表的 INSERT，目标表应已创建，用户须具备 INSERT 权限：

```bash
mysql -h FE_HOST -P 9030 -u IMPORT_USER -p TARGET_DB < compatible_inserts.sql
```

9030 为 FE 默认 SQL 端口；实际服务映射或自定义端口以用户环境为准。

批量文件导入使用 CSV/JSON 配合 Stream Load，先建好目标表并明确列映射、分隔符/转义、NULL 和日期格式。源 MySQL 仍可访问时，也可评估 JDBC Catalog 配合 INSERT INTO SELECT；需另行核对驱动、网络、类型映射和目标表。涉及持续同步时再按需求评估 CDC。本轮仅给出方案，未实现或发布导入功能。

导入后核对任务返回、过滤行/错误详情，并比较符合目标表模型预期的行数、主键及关键字段；聚合/主键表应考虑聚合或去重语义，不能只以源表原始行数判断。出现部分成功时先确认已提交范围和重试语义，避免重复重放。仅连接成功或命令退出成功不能替代数据内容核对。

## BK-33 补充：mysqldump已有基础支持，但3.5不能据此保证完整兼容（2026-10-21）

用户继续确认 mysqldump 能否完成低频、少量数据导入导出。本轮只读取官方 GitHub PR/API、StarRocks branch-3.5 源码和 MySQL 客户端源码，没有运行导出或恢复。

已确认事实：

1. 官方 PR #19227 `[Enhancement] Logical backups through mysqldump` 已于 2023-03-09 合入 main，合并提交 `34205ba71115dc73e7fdf205c991ba5c19df3435`。作者明确将其定位为小数据量逻辑备份，给出带 `--no-tablespaces` 的示例。修改增加了 `sql_quote_show_create` 兼容变量以及 LOCK/UNLOCK TABLES 的语法入口。不能笼统地称 StarRocks 从未支持 mysqldump。
2. 本轮直接读取的 branch-3.5 仍包含该兼容变量，以及 `unsupportedStatement` 下的 LOCK/UNLOCK TABLES 入口。这证明基础兼容代码存在，不证明提供 MySQL 的锁表或一致性快照语义，更不证明所有 dump 文件可恢复。
3. 官方 Issue #32076 记录了 StarRocks 3.0.0-RC01 在 mysqldump 初始化时执行 `/*!40100 SET @@SQL_MODE='' */` 遇到 EOF 语法错误。该 Issue 是旧版现场证据，不将其直接当成用户 3.5 已发生的报错。
4. MySQL 官方 8.0 的 `client/mysqldump.cc` 在连接后固定构造上述无分号的注释式 SET，并在执行失败时返回错误；5.7 的 `client/mysqldump.c` 也有该调用。它发生在开始正常导出之前，不能只讨论最终 SQL 文件中是否有兼容 DDL。
5. 本轮读取的 StarRocks branch-3.5 lexer 将该块注释放入隐藏通道；语法入口为 `singleStatement+ EOF`，空语句入口要求分号。ConnectProcessor 将原始查询文本交给 SqlParser，所查路径没有给该查询补分号。由这些源码组合推断，标准 MySQL mysqldump 与此解析路径仍有初始化兼容风险；这是源码推断，未在目标 FE 复现。
6. 官方 PR #46826 针对纯注释等 MySQL 工具兼容问题提出补充修改，并列出带 `--no-tablespaces --column-statistics=0` 的表级导出/恢复示例。本轮 GitHub API 返回 `merged=false`，网页仍为 Open；不得把它的示例或提交内容当作已随 3.5 发布的功能。其讨论也明确区分了 MySQL 原始 CREATE TABLE 选项和注释的兼容问题。

据此给用户的准确结论：StarRocks 曾加入适合少量数据的 mysqldump 基础兼容，但对于讨论中的 3.5，不能把标准 mysqldump 当成已经确认可直接完成结构、数据导出与恢复的现成方案。数据量小解决不了协议/解析兼容问题。`--no-tablespaces`、`--column-statistics=0` 分别规避对应的表空间/统计信息行为，不能据此承诺解决初始化注释式 SET。

首次咨询答复偏向 MySQL 数据迁入，未充分区分 StarRocks 自身 dump，这一边界在本轮更正。保留前述 DBeaver 数据传输建议；若用户坚持使用 mysqldump，后续需要明确实际客户端版本、目标 StarRocks 补丁/构建，再在一张代表性小表上核对完整导出及空测试库恢复。未完成该验证前，不发布固定参数为“已验证可用”，不擅自修改 FE 或替换客户端，不把失败时产生的部分 SQL 文件认作有效备份。

以上是前序源码核对时的结论，当时未执行目标 SQL、导出文件或发布兼容代码。后续现场验证已完成，见下文。仍不声称所有 StarRocks 版本或定制客户端都不能使用 mysqldump，也不把待合并修改写成已实现或已发布。

### 当前构建的mysqldump失败点

两版标准 mysqldump 均在连接初始化阶段执行以下查询时失败：

```sql
/*!40100 SET @@SQL_MODE='' */
```

关键错误为 `Getting syntax error at line 1, column 29`、`Unexpected input '<EOF>'`、错误码 1064，工具退出 2。正确账号此前已经成功执行普通 SQL；这是该构建对初始化语句的解析兼容问题，尚未进入正常表数据读取。前序关于初始化语句的源码风险在本次环境得到复现。

本次测试的关闭表空间、列统计、锁表、触发器以及 compact/no-create-info 等参数组合都未绕过这个初始化调用。不能把参数生成成功或失败后产生的文件当成有效备份；失败文件以 `.partial.sql` 标记。结论限定于本次构建与这两版标准客户端，没有修改 FE、替换或打补丁修改 mysqldump。

最初脚本曾误将 mysql 支持的 connect-timeout 选项用于 mysqldump；已移除并完整重跑。该工具参数错误不计入兼容性结论，最终两版报告均记录了服务端 1064/EOF。mysql 本身保留连接超时配置，mysqldump 使用外部进程超时约束。

### 已验证的MySQL源纯数据迁移

MySQL 8.4.2 源端导出默认完整 SQL 成功，但通过 mysql 原样送入 StarRocks 返回 1064/EOF，未得到可用的整表恢复结果。前序提到的 MySQL DDL/表模型适配边界仍成立，本次不将未执行到的每条 DDL 都描述为已经复现的报错。

已经验证可用的是：先用 StarRocks 语法建目标表，再从 MySQL 源导出纯数据 SQL，最后用 mysql 客户端发送给 StarRocks。以下是本次已验证参数组合的通用写法；配置文件与库名需要替换，源是 MySQL，不是向 StarRocks 直接运行 mysqldump：

```bash
mysqldump --defaults-extra-file=/path/source-mysql.cnf \
  --no-tablespaces --set-gtid-purged=OFF --column-statistics=0 \
  --skip-lock-tables --skip-add-locks --skip-disable-keys --skip-triggers \
  --no-create-info --compact --skip-set-charset --skip-tz-utc \
  --complete-insert SOURCE_DB sample_data > data-only.sql

mysql --defaults-extra-file=/path/starrocks.cnf TARGET_DB < data-only.sql
```

本次数据导出文件为 214 工作目录的 mysql84_to_starrocks_data_only.sql，恢复到 sr_from_mysql84_data_only_rcfdlp.sample_data，10 行与两端源数据规范输出完全一致。表结构预建属于本次过程，不能省略后将该命令说成自动迁移整个数据库。

### 已验证的StarRocks数据导出与回灌

mysql 客户端可以查询 StarRocks。此次用 JSON_OBJECT 为六个字段生成 JSON，每行一条 JSON；金额转为字符串保留 decimal 精度，日期转为字符串，NULL 由 JSON 表达，字符串中的换行和反斜杠由 JSON 序列化处理。使用 batch、raw、skip-column-names 输出为 mysql-cli-export.jsonl。

```sql
SELECT JSON_OBJECT(
  'id',id, 'name',name, 'amount',CAST(amount AS STRING),
  'event_time',CAST(event_time AS STRING), 'note',note, 'active',active
)
FROM sample_data ORDER BY id;
```

为另一测试目标预建相同 StarRocks 表后，使用 curl 配合 Stream Load 导入；认证信息通过权限 0600 的 curl 配置文件提供：

```bash
curl --config /path/stream-load.curl.conf --silent --show-error \
  --fail-with-body --location-trusted --max-time 120 \
  -H 'Expect:100-continue' -H 'format:json' -H 'read_json_by_line:true' \
  -H 'strict_mode:true' -H 'max_filter_ratio:0' -H 'label:UNIQUE_LABEL' \
  --upload-file mysql-cli-export.jsonl \
  http://BE_NODE:30480/api/TARGET_DB/sample_data/_stream_load
```

本次从 214 宿主机使用 127.0.0.1:30480 的 BE NodePort。返回 Status=Success、NumberTotalRows=10、NumberLoadedRows=10、NumberFilteredRows=0、NumberUnselectedRows=0；目标 sr_compat84_json_rcfdlp.sample_data 的规范输出与源完全一致。

直接调用 FE NodePort 30380 时，FE 返回的重定向使用 `starrocks-be-0.starrocks-be-search.starrocks.svc.cluster.local`，宿主机不能解析该域名，curl 返回 6。本次未改宿主机 DNS，改用 BE NodePort 完成验证。若使用 FE 入口，客户端需能解析并访问其返回的 BE 地址；这是网络条件，与 SQL 导出工具的初始化解析错误分开记录。

SHOW CREATE TABLE 的返回已另存 starrocks-show-create.sql；本次恢复目标使用明确的 StarRocks 建表定义，未将保存 DDL 结果描述为自动恢复所有表模型、索引、权限或其他对象。
