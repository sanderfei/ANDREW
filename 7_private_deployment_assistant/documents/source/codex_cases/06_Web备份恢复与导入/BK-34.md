
## BK-34 最终根因或已确认边界

1. `storage_type` 控制备份文件的保存位置；`source_type` 控制从哪里取数。`local` 的默认目标为 `<Web 进程工作目录>/data/cluster/<cluster>/backup/files/`。如果来源是集群，`ValidateBackupTarget()` 和 `RunBackup()` 仍会通过 SSH 到集群 Master 执行 `validateRemoteBackupTarget()`；只有 NFS 的额外可写校验由 `storage_type=nfs` 控制。
2. 当前源码中，SSH 建连失败包装为 `master ssh unavailable`；截图中的 `remote validation failed` 来自会话执行命令后的错误分支。命令没有可展示输出时，程序回退显示 `err.Error()`，因此出现单独的退出码 1。两次客户命令截图现已将具体失败项收敛到 Pod 查询为空后执行的 `test -n ''`。
3. 根因是当前前置校验固定用 `app=neo4j` 选择 Pod，与客户实际使用的 `app.kubernetes.io/name=neo4j` 标签不匹配。两者是不同的标签键，已有后者并不满足前者。客户 Pod 已为 `Running / 1/1`，结合前一次空查询与退出轨迹，确认该次前置校验被标签条件拦截。旧校验的工具、空结果和客户端检查没有具体错误说明，使报错只显示退出码；客户端能力尚未执行检查，不能推断其已经满足或缺失。
4. 另一个已确认的校验缺陷是：原 Pod 查询位于 `kubectl | head | awk` 管道中，没有检查 `kubectl` 自身的退出状态。本地模拟查询输出部分内容后返回失败时，旧校验仍继续并返回成功。该缺陷已在本地修正，但没有证据表明它就是截图报错的原因。
5. 客户手动执行截图确认 Master 交互终端能找到三个工具，`neo4j` 命名空间为 `Active`，实际 Pod 的标签和运行状态已在后续 describe 截图中得到确认。尚未执行补标签后的前置复测、Pod 内客户端检查、APOC 调用、备份归档或恢复，不能写成功能恢复。
6. 用户说明客户使用旧安装包，之后手动升级镜像。仅调整容器镜像不会自动补齐部署模板中的 `app=neo4j` 标签，该操作背景与已观察到的旧式标签相符。客户当前截图的实际镜像是 `5.26.11`，不能直接沿用本地当前安装包 `5.26.28` 的插件/配置结论；需按现场实际版本继续检查导出能力。

## BK-34 处理方案与当前实现

客户检查及手动补标签步骤（2026-10-21，本轮仅提供命令，未代客户执行）：

1. 在集群 Master 上使用具有相应权限的用户查看实际 Neo4j Pod 名、状态和 `app` 标签：

   ```sh
   kubectl get pods -n neo4j -o wide -L app
   ```

   `APP` 列为 `neo4j` 时满足该标签条件；空白或其他值均不匹配 `app=neo4j`。需要查看全部标签时使用 `kubectl get pods -n neo4j --show-labels`。先确认目标是实际 Neo4j Pod。

2. 本次客户截图已确认实际 Pod 为 `neo4j-0` 且缺少 `app` 标签，可以直接为它添加：

   ```sh
   kubectl label pod -n neo4j neo4j-0 app=neo4j
   ```

   这条命令保留现有 `app.kubernetes.io/*` 等标签，只新增 `app=neo4j`，默认拒绝覆盖已有不同值。其他环境若已有 `app` 且值不同，先核对原 Service/控制器的选择条件，不能直接加 `--overwrite` 覆盖。本次命令仅供客户执行，尚无执行结果。

3. 使用 Web 的相同条件复查：

   ```sh
   kubectl get pods -n neo4j -l app=neo4j --field-selector=status.phase=Running -o wide
   ```

   查到目标 Pod 后再执行前面的完整前置校验。查到 Pod 仅证明这一步筛选通过，还需继续检查客户端和实际备份归档。

只更新现有 Pod 的标签不会写入控制器模板，Pod 被重建后该手动标签可能丢失。长期保留需同步实际 Helm 配置/工作负载的 `.spec.template.metadata.labels`，而非只修改控制器自身的 `.metadata.labels`。StatefulSet 更新 Pod 模板标签可能按 `RollingUpdate` 策略删除并重建 Pod；持久修改前需核对实际控制器、选择器与更新策略。本轮没有修改模板或触发滚动更新。

2026-10-21 阶段定位：按截图的完整错误与当前源码，SSH 建连和会话创建已经通过，失败发生在 `session.CombinedOutput(commandText)` 执行前置校验命令时；因标签条件不匹配导致 Pod 为空，`test -n ''` 返回退出码 1。代码位置依次为 `local_backup.go:3414` 建连、`:3426` 创建会话、`:3433` 执行校验命令、`:3439` 包装返回错误。`RunBackup()` 在 `:1074` 执行这次校验，通过后才会继续到 `:1277` 的 `cmd.Exec()` 启动正式备份。不能将已定位此校验失败原因写成正式导出或备份功能已经恢复。

仅手动修改当前 Pod 不保证重建后仍在。针对已确认的 `StatefulSet/neo4j`，在主机执行：

```sh
kubectl patch statefulset neo4j -n neo4j --type=merge -p '{"spec":{"template":{"metadata":{"labels":{"app":"neo4j"}}}}}'
```

标签是键值映射；重复设置相同 `app=neo4j` 不会出现两个相同键。输出 `patched (no change)` 时模板未变化，不触发本次标签更新的滚动；实际新增或改变该标签时，`RollingUpdate` 策略会触发更新。需要确认修改其他 app 值不会影响已有 Service / 选择器；补标签后还应同步原 Helm 配置，以免日后升级回写旧模板。
