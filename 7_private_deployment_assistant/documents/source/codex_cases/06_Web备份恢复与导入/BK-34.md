## BK-34 最终根因或已确认边界

1. `storage_type` 控制备份文件的保存位置；`source_type` 控制从哪里取数。`local` 的默认目标为 `<Web 进程工作目录>/data/cluster/<cluster>/backup/files/`。如果来源是集群，`ValidateBackupTarget()` 和 `RunBackup()` 仍会通过 SSH 到集群 Master 执行 `validateRemoteBackupTarget()`；只有 NFS 的额外可写校验由 `storage_type=nfs` 控制。
2. 当前源码中，SSH 建连失败包装为 `master ssh unavailable`；截图中的 `remote validation failed` 来自会话执行命令后的错误分支。命令没有可展示输出时，程序回退显示 `err.Error()`，因此出现单独的退出码 1。两次客户命令截图现已将具体失败项收敛到 Pod 查询为空后执行的 `test -n ''`。
3. 根因是当前前置校验固定用 `app=neo4j` 选择 Pod，与客户实际使用的 `app.kubernetes.io/name=neo4j` 标签不匹配。两者是不同的标签键，已有后者并不满足前者。客户 Pod 已为 `Running / 1/1`，结合前一次空查询与退出轨迹，确认该次前置校验被标签条件拦截。旧校验的工具、空结果和客户端检查没有具体错误说明，使报错只显示退出码；客户端能力尚未执行检查，不能推断其已经满足或缺失。
4. 另一个已确认的校验缺陷是：原 Pod 查询位于 `kubectl | head | awk` 管道中，没有检查 `kubectl` 自身的退出状态。本地模拟查询输出部分内容后返回失败时，旧校验仍继续并返回成功。该缺陷已在本地修正，但没有证据表明它就是截图报错的原因。
5. 客户手动执行截图确认 Master 交互终端能找到三个工具，`neo4j` 命名空间为 `Active`，实际 Pod 的标签和运行状态已在后续 describe 截图中得到确认。尚未执行补标签后的前置复测、Pod 内客户端检查、APOC 调用、备份归档或恢复，不能写成功能恢复。
6. 用户说明客户使用旧安装包，之后手动升级镜像。仅调整容器镜像不会自动补齐部署模板中的 `app=neo4j` 标签，该操作背景与已观察到的旧式标签相符。客户当前截图的实际镜像是 `5.26.11`，不能直接沿用本地当前安装包 `5.26.28` 的插件/配置结论；需按现场实际版本继续检查导出能力。

### 初步问题原因与源码边界

本节为取得本次现场标签截图之前的源码分析；最新截图与 Git 历史已进一步收敛方向，见下方“最新截图与旧 Web 预检历史比对”。本轮只读核对本地 `release` 后端源码和已解压的客户旧包，三处 Pod 选择逻辑并不一致：

| 路径 | 当前源码行为 | 影响 |
|---|---|---|
| `remoteValidationCommand()` 的 Neo4j 预检查 | 仅查询 `app=neo4j` 且 `status.phase=Running` 的 Pod，使用 `-o name`；无回退 | 旧包只有标准标签时，预检查会得到空值 |
| Neo4j 数据库列表 | 先按同一标签查询；为空时回退到命名空间内第一个 Running Pod | 能列库不代表严格标签预检查也会通过 |
| 正式备份脚本 `first_pod()` | 先按同一标签查询；为空时先回退到任意 Running Pod，再回退到任意 Pod | 与预检查口径不同；回退也可能取到其他用途或未就绪的 Pod |

### 同日补充：修改配置时报错与保存、校验接口的区别

用户补充“修改配置也有类似报错，感觉是配置文件配置问题”，随后明确操作是“Web 备份设置中保存配置”。最新请求证据已确认错误来自 `POST /api/v1/clusters/<cluster>/backups/config/neo4j/validate`：响应为 `code=10000`、`msg=OK`，但 `data.target=neo4j`、`data.ready=false`，`data.message` 包含 `remote validation failed` 及 `.items[0]` 对空列表越界。即正常业务响应中承载了目标校验失败；保存 PUT 的结果仍未提供，不能据此认定保存文件失败。

当前后端将这些操作分开：`PUT /api/v1/clusters/:cluster/backups/config/:target` 对应 `SaveBackupTargetConfig()`，只做配置字段/NFS检查并写入 `backup/config.json`，不调用远程 Pod 预检查；`POST .../backups/config/:target/validate` 与 `POST .../backups/targets/:target/run` 才会对集群来源调用 `validateRemoteBackupTarget()`。本次证据现已对应到独立的 validate 接口，与当前源码将远程预检查放在校验路径的行为一致；不能写成保存 PUT 直接调用远程预检查。用户触发位置虽是保存界面，但本轮没有检查前端，具体请求时序和保存 PUT 是否成功仍未确认。实际执行使用 JSONPath，而当前本地预检查使用 `-o name`，部署版本或实际生成命令的差异仍需核对；标签是否导致本次空列表，也仍需在 Master 上使用与 Web 相同的 SSH 用户和 kubeconfig 对照查询。
