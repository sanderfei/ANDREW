# BK-42：MariaDB schema-sync apply 提示 prepare.done 不存在

项目：g_web_installer。记录日期：2026-11-03。状态：旧版 apply 请求过早原因已确认；新版 121 自动结构同步、Web restore 隔离验证及用户授权的 214 测试集群恢复已实测，其他业务健康和失败路径未验证。

## 环境与表现

Web 后端直接运行在 121 宿主机，操作的 Web 集群名为 `k8s_test`。用户发起 MariaDB schema-sync prepare 后，使用返回的 prepare PID 调用 apply，接口返回：

```text
MariaDB schema-sync artifact prepare.done is unavailable: stat .../history/<prepare-pid>/prepare.done: no such file or directory
```

本次 prepare PID 为 `2026-11-02_21-38-58.285_mariadb_schema_sync_prepare`。该错误只说明 apply 检查时未找到完成标记，不能单凭它断言缺少命令或数据库执行失败。

## 现场与源码证据

- 121 `logs/server.log` 第 5539 行记录 prepare 请求在 `2026-11-02 21:38:58 EST` 返回 HTTP 200，第 5540 行记录同一 prepare PID 的 apply 请求在 `21:38:58 EST` 返回 HTTP 500。该任务 `execute.log` 显示 prepare 在 `21:39:04 EST` 完成，此时才生成 `prepare.done`；换算为北京时间 `2026-11-03 10:39:04`。只读检查时该标记已存在，`b_import_warnings.log` 为空。
- 该任务目录检查时未发现 `apply.started` 或 `restore.done` 标记；这不等于已完整验证 MariaDB 的业务数据和结构。
- 121 的 prepare 所需命令均存在。排查现场没有依据认定本次是缺工具导致，当前检查不代表此前所有时刻环境必然相同。
- 当时的旧版源码 `internal/service/importdata/mariadb_schema_sync.go` 中，prepare 异步启动并返回 PID；脚本完成方案生成后才创建 `prepare.done`。独立 `apply` 会先检查同一 prepare PID 的完成标记、方案、备份和库清单，缺失即直接返回错误，并不会开始执行增量 SQL。
- 现场日志已证实 apply 在 prepare 完成前发出：21:38:58 请求检查完成标记时，prepare 尚未到 21:39:04 的完成步骤，因此返回标记不存在。HTTP 200 和 PID 只表示 prepare 任务已启动，并非异步任务已经执行完成。

## 实现更新与现场验证

用户授权后，中央提交 `38f56b5` 已发布到 121 宿主机直接启动的 Web 后端。新版 `prepare` 在同一个异步任务内依次备份、生成差异、自动执行；独立 `apply` 路由已删除，`plan` 和 `restore` 保留。旧版尚未执行的方案不能通过新版独立 apply 路由继续执行，需要重新发起 prepare。历史排查时旧版“下载方案后人工调用 apply”的流程不适用于该新版。

2026-11-03 用户授权在 `k8s_test` 验证：

- 登录后调用 `POST .../prepare` 返回 HTTP 200，PID 为 `2026-11-02_22-03-00.13_mariadb_schema_sync_prepare`；仅返回 PID 不作为完成证明。
- 同一 PID 的 WebSocket 任务日志显示 prepare 在 `2026-11-02 22:03:00–22:03:04 EST`、自动 apply 在 `22:03:04–22:03:06 EST`，最终成功；相应北京时间为 2026-11-03 11:03:00–11:03:06。
- 121 上传包与 214 生成包 SHA256 一致，包内为 B、C 两个 SQL；任务完成标记和备份存在，导入 warning 文件为空，临时数据库已清理。
- 214 实际库查询：A 包含 a1、a2，B 包含 b1、b2、b3，C 包含 c1、c2；升级前的 a1、a2、b1、b2 四张表各保留 100 行，b1 的旧字段保留且新增 `new_code` 和 `new_note`。新增的 b3、c1、c2 各为 0 行，符合结构同步不会导入目标包业务数据的行为。

## 备份与当前数据库完整性核验

2026-11-03 用户进一步要求核验备份和当前数据库。将 121 指定 prepare 任务的备份完整导入 214 集群的隔离临时 MariaDB 10.11.10，导入退出码为 0。初次比较对数字列直接使用 `HEX()`，可能丢失小数精度，故初次行哈希结果已撤销，不作为一致性证据。

北京时间 11:13:16–11:13:18 采用 `HEX(CAST(col AS BINARY))` 对恢复库与 214 当前数据库重新计算备份原有全部列、全部行的哈希多重集，包含 NULL 和重复行；备份所含 10 库 79 表的原字段定义、行多重集和行数均为 79/79 一致，0 缺失、0 错误。备份唯一 double 列所在表为空，因此本次没有浮点精度比较问题。当前库额外存在 b.b3、b.b1 的两个新字段和 c 库，属于本次结构同步的预期新增项。

北京时间 11:14:16–11:14:26，另外核对恢复涉及的 79 表的 207 个索引和 285 条索引列定义，结果两边相同；10 库的触发器、例程和事件两边数量均为 0。这些结果只覆盖列出的对象及比较项目。

两实例是分时读取且没有冻结实时写入，结论仅覆盖各自的比对时刻，不能保证之后的变化已备份。上述步骤是备份导入隔离实例；下面另行记录 Web restore API 的隔离功能验证。

## Web restore API 隔离验证

2026-11-03 使用 121 实际 Web 后端的隔离集群 `schema_restore_verify_2071ca031b9d`，将真实 prepare PID `2026-11-02_22-03-00.13_mariadb_schema_sync_prepare` 的备份、清单及标记复制到隔离集群任务目录。隔离 MariaDB Pod 使用独立的 `/var/lib/mysql` emptyDir，`lower_case_table_names=1`；先导入该备份并执行真实计划，重现原 10 库以及 B3 和新 C 库等结构同步后的状态。

调用隔离集群的 Web restore 接口返回 HTTP 200，restore 任务 PID 为 `2026-11-02_22-22-03.579_mariadb_schema_sync_restore`；WebSocket 日志终态成功。恢复后为 10 库 79 表，A1、A2、B1、B2 各 100 行，B1 恢复旧字段，新增 B3 和 C 库被删除。

与另一独立备份恢复 Pod 比对，664 个字段、207 个索引及 285 条索引列定义，以及 79 表全部行的 SHA256 多重集均一致，零错误。double 列所在表为空。此结果验证了 121 Web restore 访问隔离 MariaDB 的数据恢复路径；隔离验证时 214 测试集群尚未执行 restore，仅只读抽样未变。随后用户另行授权执行真实测试集群恢复，结果见下。

测试中通过仅监听本地回环的临时 sshd 模拟了组件 Helm/Kubernetes 健康检查，不能将其视为真实组件健康检查；MariaDB 恢复则通过真实 121 服务和双 SSH 隧道指向实际隔离 Pod。该隔离验证不覆盖真实集群组件健康判断或其他生产环境回退。 验证完成后，121 隔离集群目录、SSH 测试服务及 tmpfs 中的密钥配置、两个隔离 Pod（emptyDir）和两条 SSH 隧道均已清理，相关端口监听已确认解除。此前用于备份核验的临时 MariaDB Pod 虽有 emptyDir，实际 `/var/lib/mysql` 使用 Pod 临时可写层，Pod 删除后数据一并清除；本轮 restore Pod 已正确将该路径挂载到独立 emptyDir。

## 121 Web 对 214 测试集群实际恢复验证

2026-11-03，用户明确授权直接恢复 214 测试环境。通过 121 Web 对 `k8s_test` 的 prepare PID `2026-11-02_22-03-00.13_mariadb_schema_sync_prepare` 发起 `POST restore`，HTTP 200 返回任务 PID `2026-11-02_22-30-14.496_mariadb_schema_sync_restore`；同 PID 的 WebSocket 日志终态成功。服务端日志时间为 2026-11-02 22:30:14–22:31:43 EST，即北京时间 2026-11-03 11:30:14–11:31:43。`restore.started` 和 `restore.done` 均存在。

214 实际查询显示恢复后有 10 个业务库、79 张表；A 的 a1/a2 和 B 的 b1/b2 四表各 100 行；B1 字段为 `id`、`name`、`old_code`、`old_note`，C 库、B3 表及临时库不存在。本次实际回退范围是备份中的全部 10 库，不仅是 A 和 B。

随后按用户要求，于北京时间 11:39:17–11:39:20，将真实 214 恢复后的数据库与由原 121 备份导入的隔离参考 Pod 逐表对照。双方 10 库、79 表、664 字段、207 个索引及 285 条索引列定义一致；79/79 表的全行 SHA256 多重集和行数一致，差异及查询失败均为 0。行比对区分 NULL 并使用 `HEX(CAST(col AS BINARY))`，保留重复行；唯一 double 列对应表两侧均为 0 行。真实 C 库不存在。

独立参考 Pod 已删除并确认不存在，其 emptyDir 随 Pod 清理。两侧数据是分时快照，未冻结业务写入，结论仅覆盖比对时刻。未验证其他业务的运行健康，不能将本次测试集群恢复结果外推为其他环境的恢复结果。

## 排查和处理

1. 新版调用 prepare 后，保存返回 PID，通过 WebSocket 日志接口 `/api/v1/logs/cluster/<cluster>/tail/<prepare-pid>/execute.log` 等待该任务最终结果；接口返回 PID 不代表备份、差异生成或自动执行完成。
2. 注意新版 prepare 会自动执行差异 SQL；如需预审 SQL，不能沿用旧版 prepare 后再手工调用独立 apply 的流程。失败时结合任务日志及该 PID 的方案、备份、标记和 `b_import_warnings.log` 判断，不要手动创建完成标记。
3. 如需回退，先评估原 prepare 备份时间和回退覆盖范围，再根据新版 restore 接口使用对应 prepare PID；全量恢复可能覆盖备份之后的数据。隔离环境及 214 测试环境均已实测 restore，其他生产环境回退尚未验证。

## 验证和边界

旧版请求先于 prepare 完成已由现场请求日志证实。新版本次已验证 121 Web 发起的 prepare、同任务自动 apply 与 214 实际库表、字段和行数，`verified` 覆盖本次正向结构同步、Web restore 隔离验证，以及 214 测试集群恢复后的全库行、字段和索引比对。随后已对备份执行隔离导入，并以类型保真方法重新核对 10 库 79 表原字段定义、全部行哈希多重集与行数，全部一致；207 个索引及 285 条索引列定义也已比对。两实例分时读取且未冻结写入，结果只覆盖比对时刻；随后先测试 Web restore 的隔离路径，再经用户授权对 214 测试集群执行真实恢复并核对指定结构和行数。真实恢复后已与隔离参考实例对 10 库 79 表逐行及定义比对，结果覆盖比对时刻；未验证自动 apply 失败后的处理、其他生产环境回退、索引差异或业务应用完整性。
