## 源码证据与边界

本地 Web checkout `b6da1292de66` 的 `internal/service/backup/milvus_discovery.go` 先列举 `milvus` 命名空间的 Pod 和 Service，再从 Pod 中寻找：

1. 标签 `app.kubernetes.io/component=proxy` 和 `app.kubernetes.io/instance=milvus`；
2. Pod 不在删除中、phase 为 Running、Pod Ready 条件为 True；
3. 普通容器镜像名包含 `/milvus:` 或 `/milvus@`，或以 `milvus:` 开头，且对应容器状态为 Running、Ready。

现场为 standalone 部署，且没有符合要求的 Proxy Pod，与本地源码仅查找分布式 Proxy 的条件不兼容；Pod 的 `component=standalone` 也不是源码读取的标签键。现场输出支持这一兼容性判断，不能由此断言 Milvus 服务不健康；也不能由本地源码推定现场正在运行完全相同的 Web 二进制。

当前源码在选择成功后还会匹配 gRPC Service、读取运行配置并解析对象存储，随后准备备份；此错误处于这些后续步骤之前，不能据此判断数据库访问、对象存储、归档或恢复是否正常。历史部署差异见 [BK-38](BK-38.md)，不能将其旧的 standalone 前置校验故障直接套用本次现场。

版本历史：Web 提交 `1538dcd` 之前的 `internal/service/backup/local_backup.go` 优先通过 `component=standalone` 选取 Pod，必要时按包含 `standalone` 的 Running Pod 名称回退；该提交引入分布式备份发现并切换为只查找 Proxy。提交 `21b5aa0` 后续将 GC 控制地址改为 Proxy Service。上述历史说明筛选策略发生过变化，并不能证明旧实现能在本现场完成备份；现场运行 Web 版本及其历史尚未核实。
